# V93K RAG 项目痛点与实际开发难点

> 审阅基线：2026-09-14 当前工作区代码  
> 适用范围：`main.py`、`api/`、`rag_qa/`、`web_ui/`、`scripts/`、`config.ini`  
> 说明：本文区分“代码中已确认的问题”和“随着数据量/并发量上升后容易暴露的风险”，用于排期、技术评审和后续重构。

## 1. 项目现状概览

本项目是一套面向 V93000/V93K 领域知识的 RAG 问答系统，核心链路为：

```text
多格式文档 → 文本提取/OCR → 父子分块 → BGE-M3 稠密/稀疏向量
                                        ↓
用户问题 → FAQ 匹配 → 意图与策略路由 → 混合检索 → 父块还原 → Rerank
                                                           ↓
                                     LLM 生成/SSE 输出 → MySQL 会话与摘要
```

项目已经具备 FAQ 快速路径、混合检索、父子块、重排、SSE、会话历史和 RAGAS 评估等完整能力。实际开发难点主要不在“把流程跑通”，而在于保证数据质量、索引一致性、并发安全、性能、可评估性和生产安全。

## 3. 详细痛点与开发难点

### 3.1 配置与接口安全（P0）

**当前证据**

- `config.ini` 中直接保存了 LLM API Key 和 MySQL 密码，并且该文件处于项目代码目录中。
- `POST /api/rebuild_index` 与 `POST /api/faq/reload` 没有鉴权或权限控制。
- `main.py` 的 CORS 配置允许任意来源、任意方法和任意请求头。
- `/api/ask` 没有认证、限流、请求大小限制和配额控制。
- SSE 异常事件会把 `str(e)` 直接发送给前端，可能暴露内部错误细节。

**实际影响**

- 一旦仓库、压缩包、日志或屏幕共享泄漏，凭据可能被直接使用。
- 能访问服务的任何客户端都可以触发耗时且具有破坏性的全量索引重建。
- 对公网开放后，LLM 调用费用和 CPU 资源可能被恶意消耗。
- `session_id` 只是客户端提供的短 ID，不是访问凭证；知道 ID 的用户可能读取并影响同一会话上下文。

**建议**

1. 立即吊销并轮换当前已写入文件的 API Key；密码也应更换。
2. 仓库只保留 `config.example.ini`，真实凭据通过环境变量或密钥管理服务注入。
3. 管理接口和普通问答接口分别鉴权；重建、FAQ 重载至少要求管理员身份。
4. 将 CORS 改为明确的前端域名白名单，并增加反向代理层限流、超时和请求体上限。
5. 对外只返回稳定错误码与通用消息，详细异常保留在服务端日志。

**验收标准**

- 仓库历史和当前文件不再包含有效凭据；密钥扫描通过。
- 未认证请求无法调用重建和 FAQ 重载接口。
- 问答接口具备按用户/IP 的速率限制，CORS 不再使用 `*`。

### 3.2 索引重建的原子性与数据一致性（P0）

**当前证据**

- `api/routes.py` 中的重建流程先执行 `store.clear()`，再执行 `store.add_documents(...)`。
- `VectorStore.clear()` 会直接删除 children/parents 两个 Chroma collection，然后原名重建。
- 重建过程没有全局读写锁、任务状态、双缓冲 collection 或失败回滚。
- 在线问答与重建接口可以同时访问同一个全局 `VectorStore` 实例。
- 文档 ID 使用 `doc_<遍历序号>_parent_<序号>`，文件增删或遍历顺序变化会使大量 ID 改变，不利于增量更新和问题追踪。

**实际影响**

- 重建期间用户可能查到空库、半成品索引，或者遇到 collection 已删除异常。
- 新索引写入中途失败时，旧的可用索引已经被删除。
- 多个进程/实例同时运行时，内存稀疏索引与 Chroma 状态可能不一致。
- 每次新增一份文档都需要全量 OCR、分块、Embedding 和写库，数据量增长后不可接受。

**建议**

1. 使用带版本号的临时 collection 完整构建新索引，校验数量与抽样检索后再原子切换别名/活动版本。
2. 将重建改为后台任务，提供 `queued/running/succeeded/failed` 状态，避免 HTTP 请求长时间占用。
3. 对查询和切换动作增加进程级/分布式读写协调，确保用户始终读取一个完整版本。
4. 以“规范化相对路径 + 内容哈希 + 分块序号”生成稳定 ID，记录文档哈希和索引版本，实现增量新增、更新和删除。
5. 构建失败保留旧索引，并输出失败文件清单，而不是静默跳过后继续发布不完整索引。

**验收标准**

- 重建期间连续查询无空结果窗口。
- 任意构建步骤失败后，线上仍使用上一个完整索引。
- 单文档更新只重算受影响的分块；可以查询当前活动索引版本和构建状态。

### 3.3 多格式文档解析与 OCR 质量（P1）

**当前证据**

- PDF、DOCX、PPTX、图片走不同解析器，最终都被压平成纯文本，表格结构、标题层级、页码和图文位置关系保存有限。
- PDF 只对达到页面宽高比例阈值的嵌入图片执行 OCR，小图中的关键错误码、波形标注和局部截图可能被漏掉。
- `ocr_pdf.py` 将 `extract_image()` 返回的编码图片字节直接按高宽 `reshape`，对 PNG/JPEG 等压缩字节存在解析失败风险；应先用 Pillow/OpenCV 解码。
- DOCX/PPTX 图片 OCR 中存在吞掉异常的 `except Exception: pass`，构建结束后不容易知道哪些图片没有识别成功。
- `load_documents()` 以文件 stem 全局去重；不同目录下同名但内容不同的文档会被跳过。
- 单个文件加载失败时只记录日志并继续，最终索引仍可能被视为“重建成功”。

**为什么难**

V93K 资料通常包含命令、错误码、引脚名、表格、时序图和中英文混排。OCR 中一个字符错误就可能把可检索的精确术语变成完全不同的 token。仅以“成功提取到字符串”判断质量远远不够。

**建议**

1. 为每类格式建立包含表格、图片、页眉页脚、中英文术语的黄金样例。
2. 保留页码、章节、表格行列、图片位置等 metadata，引用结果至少能定位到文件与页/章节。
3. 修复 PDF 图片解码路径，记录 OCR 耗时、置信度、空文本率和异常文件。
4. 将“解析失败/空文本/低质量 OCR”设为构建告警或发布阻断条件。
5. 去重键改为相对路径或内容哈希，不再只使用 stem。

**验收标准**

- 黄金文档的标题、表格关键字段、错误码和图片文字可被稳定提取。
- 构建报告能列出每个文件的页数、字符数、OCR 页数、错误与告警。
- 任一来源可从回答追溯到具体文件和页码/章节。

### 3.4 切分、混合检索、路由与重排的联合调优（P1）

**当前证据**

- 父块 1200、子块 300、重叠 50、`retrieval_k=5`、`candidate_m=3` 均是固定全局参数。
- 稠密与稀疏结果使用固定 `RRF_K=60` 融合，没有按文档类型或查询类型调权。
- FAQ 使用固定余弦阈值 0.85；README 已说明该阈值尚未由真实 FAQ 数据集标定。
- FAQ 未命中后先调用 LLM 做领域与策略路由；HyDE、子查询和回溯策略还会额外调用 LLM 改写查询。
- Reranker 只对还原后的少量父块排序，召回阶段丢失的内容无法被重排补救。

**实际影响**

- 参数之间强耦合：调大块提升上下文完整性，却可能降低定位精度并增加 Prompt token；调小块则可能切断步骤、表格与上下文。
- FAQ 阈值过低会把相似但不同的问题直接返回固定答案，过高又失去快速路径价值。
- 路由错误会把专业问题当闲聊，或为简单问题引入多次昂贵 LLM 调用。
- 仅看最终答案很难判断问题出在解析、切分、召回、重排、路由还是生成。

**建议**

1. 建立分层标注集：FAQ 正/负例、路由标签、相关文档/分块、标准答案分别标注。
2. 做参数矩阵实验，至少比较 chunk、overlap、top-k、candidate-m、FAQ 阈值、RRF 与 rerank 开关。
3. 保存每次请求的路由结果、改写查询、稠密/稀疏排名、RRF 分数、rerank 分数与最终引用。
4. 对精确错误码、API 名、STIL 关键字优先走词法/规则路径；复杂解释题再使用 HyDE 或子查询。
5. 增加“无可靠证据”阈值，让系统可以拒答，而不是只要检索到内容就生成。

**验收标准**

- FAQ 有独立 precision/recall，并以业务可接受的误命中率选择阈值。
- 路由准确率、Recall@K、MRR/nDCG、答案正确性和引用正确性均有基线。
- 每次参数或模型变更都能与固定基线报告对比。

### 3.5 稀疏检索的性能、内存与持久化（P1）

**当前证据**

- 稀疏词项权重只保存在进程内存，服务每次启动都从 Chroma 读取全部子块并重新调用 BGE-M3 计算稀疏向量。
- `SparseIndex.search()` 对查询中的每个 token 遍历所有文档权重，属于近似 `O(查询词项数 × 子块数)` 的 Python 循环。
- 类中维护了 `doc_freq`，但当前检索没有使用倒排表或基于 doc frequency 的剪枝。
- 每个 worker 都会各自加载一份模型和稀疏索引，横向增加 worker 会明显放大内存占用。

**实际影响**

- 知识库越大，冷启动越慢；Kubernetes/进程重启可能长期处于不可服务状态。
- 并发查询时 Python 循环与 CPU 模型推理相互争抢资源。
- 多进程部署可能因模型与索引重复占用内存而无法简单扩容。

**建议**

1. 将 lexical weights 随索引版本持久化，启动时直接加载，避免全量重算。
2. 构建 token → posting list 的倒排索引，仅遍历命中的文档；或采用成熟 BM25/搜索引擎组件。
3. 对启动、Embedding、稀疏检索、Chroma 查询和 rerank 分别做规模压测。
4. 明确进程模型：单进程模型服务 + 多 API worker，或把 Embedding/Rerank 独立成推理服务。

**验收标准**

- 在目标知识库规模下，冷启动时间、单查询 P95 和内存占用有明确上限。
- 重启不再重新计算全部稀疏向量。
- 查询性能增长接近命中 posting 数，而不是全部子块数。

### 3.6 会话历史与后台摘要并发（P1）

**当前证据**

- 每次非 FAQ 问答完成后创建一个新的 daemon 线程重建摘要，没有线程池、队列、去重、重试或每 session 锁。
- 代码注释已经明确说明“快速连发可能丢更新”。
- 多个线程会读取相同旧摘要、各自调用 LLM，最后完成的任务覆盖 `summaries`，不保证它覆盖的轮次最多。
- `turn_count` 使用 `3 + len(old_turns)` 计算，但摘要生成时又把“旧摘要 + 当前查出的全部旧轮次”重新输入，随着会话增长可能重复总结、成本持续上升。
- daemon 线程在进程退出时会被直接终止，结果没有可靠交付保证。

**实际影响**

- 连续提问时后续回答可能使用陈旧或倒退的摘要。
- 长会话的摘要 Prompt 越来越大，增加延迟和调用费用。
- 请求突发会产生大量线程和并行 LLM 请求，引发限流。

**建议**

1. 使用有界任务队列和固定 worker；同一 session 串行执行并合并重复任务。
2. 摘要表增加 `covered_turn_id` 或版本号，采用 compare-and-swap，拒绝旧任务覆盖新摘要。
3. 仅总结上次 `covered_turn_id` 之后、且不属于最近 N 轮的增量记录。
4. 为失败任务增加退避重试、死信记录和可观测状态；进程关闭时优雅等待在途任务。

**验收标准**

- 同一会话连续快速发送 20 轮后，摘要覆盖轮次单调递增且内容不丢失。
- 后台任务数量有上限，LLM 限流时不会无限创建线程。
- 长会话单次摘要输入规模稳定，不随总轮数线性增长。

### 3.7 自动化测试与回归保障不足（P1）

**当前证据**

- 当前工作区没有可执行的项目单元测试/集成测试目录；原有 smoke 脚本处于删除状态。
- OCR、父子块映射、RRF、source filter、FAQ 阈值、SSE 事件、MySQL 摘要等关键逻辑缺少自动化边界测试。
- 全局单例与本地模型/Chroma/MySQL 强耦合，使测试隔离和依赖替换更困难。

**实际影响**

- 检索参数和 Prompt 的小改动可能悄悄改变路由、召回或回答结果。
- 只有把完整模型、数据库和外部 LLM 都启动后才能验证，反馈周期长且结果不稳定。
- 依赖升级后兼容性问题往往到运行期才暴露。

**建议**

1. 先补纯逻辑单测：FAQ 校验/匹配、RRF、父块还原、分块 ID、SSE 编解码、配置校验。
2. 用 fake Embedding、fake LLM、临时 Chroma 和测试数据库做组件集成测试。
3. 增加一套固定小语料的端到端离线测试，覆盖 FAQ、knowledge、chitchat、无结果、过滤和流式异常。
4. CI 分层执行：快速测试每次提交运行；模型/OCR/RAGAS 测试按需或定时运行。

**验收标准**

- 核心纯逻辑测试无需下载模型、连接 MySQL 或调用外部 API 即可执行。
- 每条关键路径都有成功、失败和边界场景。
- 检索或 Prompt 变更未通过基线阈值时不能发布。

### 3.8 评估体系不能完整代表线上效果（P1）

**当前证据**

- 当前评估仅计算 `context_precision` 和 `context_recall`。
- 评估运行器固定使用 `direct` 策略，绕过线上 FAQ 优先和 QueryRouter 的实际决策。
- 评估仍调用远程 LLM 生成答案和担任 RAGAS judge，存在模型波动、超时、限流和成本。
- 评估集只有 25 道题，难以覆盖错误码、API、概念、步骤、多轮追问、越界问题和 OCR 文档等场景。

**实际影响**

- 离线检索指标提升不代表线上路由、FAQ 或最终答案更好。
- 同一版本重复评估可能因 judge 波动得到不同结论。
- 没有延迟、费用、拒答质量和引用一致性指标，无法平衡效果与工程成本。

**建议**

1. 增加线上等价评估：按真实链路跑 FAQ、路由、策略选择、检索和生成。
2. 指标分层：FAQ、路由、检索、答案忠实度/正确性、引用、延迟、失败率、token/费用。
3. 扩充并版本化数据集，按问题类型、来源和难度分桶报告。
4. 固定评估模型/参数，保存原始逐题结果；关键样本增加人工复核。

**验收标准**

- 报告同时给出总体与分桶结果，并能追踪到单题失败原因。
- 至少覆盖完整线上路径，而不只是 direct retrieval。
- 版本上线前有明确的质量门槛和允许退化范围。

### 3.9 环境、依赖与部署可移植性（P2）

**当前证据**

- `config.ini` 和 README 中包含 Windows 绝对路径及另一个工程目录中的 reranker 权重路径。
- `requirements.txt` 固定了大量直接或间接依赖，并混入 CUDA 构建的 PyTorch；CPU 配置与 CUDA 包并存。
- FastAPI 启动时同步加载 Embedding、Reranker、Chroma 稀疏索引和 FAQ 向量，任何一步过慢都会拉长 readiness。
- MySQL 不可用时启动只记录 warning，但后续每轮读写历史仍会经历连接超时。

**实际影响**

- 换机器、容器化或部署到 Linux 时需要大量手工修改。
- Python、Transformers、FlagEmbedding、Torch、RAGAS 与 LangChain 之间容易出现版本兼容问题。
- “进程已启动”不等于“模型和依赖已就绪”，运维探针容易误判。

**建议**

1. 所有模型和数据路径使用环境变量/相对目录，启动时做统一配置校验并给出可操作错误。
2. 区分顶层依赖与锁文件，拆分 runtime/dev/eval/CPU/GPU 依赖集合。
3. 容器或标准化启动脚本固定 Python 与系统库版本；模型作为挂载卷或受控制品管理。
4. 区分 liveness 与 readiness；健康检查应覆盖活动索引、模型状态和必要依赖。

**验收标准**

- 新环境仅通过文档化变量即可启动，不依赖其他工程的绝对路径。
- CPU 与 GPU 环境各有可复现的依赖锁定和冒烟测试。
- readiness 只有在模型、索引和必要服务可用后才成功。

### 3.10 可观测性与故障定位（P2）

**当前证据**

- API 主要返回端到端 `elapsed_ms`，没有解析、路由、查询改写、Embedding、Chroma、稀疏检索、rerank、首 token、生成、MySQL 等分阶段耗时。
- 日志以文本为主，没有统一 request ID、索引版本、模型版本、命中分数和状态码字段。
- `/api/health` 只报告模型名、collection 名和子块数，不能区分依赖降级与完整健康。
- Generator 捕获 LLM 异常后返回一段普通答案，API 仍可能表现为成功，监控难以统计真实失败率。

**实际影响**

- 用户反馈“很慢”或“答错”时，难以快速区分检索、模型、数据库还是网络问题。
- 上游 API 故障会被业务兜底文本掩盖，成功率看起来正常但实际不可用。

**建议**

1. 为每次请求生成 request ID，并记录阶段耗时、路由、候选数量、分数、索引/模型版本。
2. 引入结构化日志与指标：QPS、P50/P95/P99、首 token、错误率、FAQ 命中率、无结果率、LLM 限流率。
3. 业务降级必须携带机器可识别的 error/degraded 状态，不应只靠答案字符串判断。
4. 对慢请求保存精简 trace，避免日志中记录完整敏感问题和答案。

**验收标准**

- 一次请求可按 request ID 还原完整耗时链路。
- 能区分正常回答、无知识拒答、LLM 降级和系统异常。
- 告警能定位到具体外部依赖或处理阶段。

### 3.11 单机并发与容量上限（P2）

**当前证据**

- Embedding、Reranker、Chroma、FAQ 和 RAGSystem 都以进程内全局单例运行。
- CPU 上同时执行 BGE-M3、CrossEncoder、OCR 和 Python 稀疏检索，资源竞争明显。
- 每次 MySQL 操作创建新连接，没有连接池。
- SSE 请求会维持长连接；断开检测和生成取消机制不明确，客户端离开后上游 LLM 可能仍在生成。
- 各级没有统一的并发上限和背压机制。

**实际影响**

- 少量慢请求即可占满线程或 CPU，导致所有请求延迟一起上升。
- 简单增加 Uvicorn worker 会重复加载大模型和索引，可能先遇到内存瓶颈。
- 数据库连接数、LLM 并发和后台摘要线程在流量突发时可能同时放大。

**建议**

1. 建立容量基线，测量单机在不同并发下的吞吐、P95、内存、CPU 和错误率。
2. 对在线问答、索引任务、OCR 和摘要任务分池限流，设置队列长度与拒绝策略。
3. MySQL 使用连接池；客户端断开时尽可能取消上游生成与后续落库任务。
4. 根据压测决定模型推理与 API 是否拆分服务，而不是直接增加 worker。

**验收标准**

- 明确支持的并发数、最大知识库规模和资源规格。
- 超载时可控降级或快速拒绝，不出现无限排队、线程膨胀和进程 OOM。

### 3.12 会话数据治理与用户体验（P2）

**当前证据**

- 前端把 `session_id` 长期保存在 `localStorage`，没有“新建会话/清空历史/过期”机制。
- 数据库表没有用户 ID、租户 ID、过期时间和清理任务。
- `session_id` 为截断到 8 位十六进制的 UUID，适合演示标识，不适合作为安全隔离依据。
- 前端展示的“置信度”由请求耗时推算，并不代表检索相似度、rerank 分数或答案可信度。

**实际影响**

- 共用浏览器、复制 localStorage 或 ID 碰撞时可能串用上下文。
- 历史问答和摘要无限增长，带来存储、隐私和合规风险。
- 把延迟包装成置信度会误导用户对答案可靠性的判断。

**建议**

1. 会话绑定真实用户/租户，并使用高熵不可猜标识；服务端校验会话所有权。
2. 增加新建、列出、删除和过期会话能力，制定保留周期与脱敏规则。
3. 取消伪置信度；若要展示可信程度，应由检索覆盖、证据一致性或校准模型产生，并解释含义。
4. UI 明确区分 FAQ 固定答案、基于文档生成、闲聊、无证据拒答和系统降级。

**验收标准**

- 用户无法访问其他用户的会话；会话支持主动删除和自动过期。
- UI 不再用耗时计算置信度，答案类型和来源状态清晰可见。

## 4. 推荐实施路线

### 第一阶段：先消除高风险问题（1～2 周）

- 轮换凭据，移除仓库中的秘密，补 `.env/config.example.ini` 使用说明。
- 为重建和 FAQ 重载接口增加认证、权限与审计。
- 将索引重建改成“新版本构建 → 校验 → 切换”，失败保留旧版本。
- 修复 PDF 图片解码，输出可检查的文档构建报告。
- 恢复最小测试框架，覆盖 FAQ、RRF、父子块、source filter、SSE 和配置。

### 第二阶段：建立质量闭环（2～4 周）

- 扩充并分层标注评估集，建立 FAQ/路由/检索/答案/引用指标。
- 建立完整链路的离线基线与参数实验脚本。
- 增加结构化日志、request ID、阶段耗时和索引/模型版本。
- 修复摘要并发覆盖，改为有界队列和增量摘要。

### 第三阶段：解决规模与部署问题（4～8 周）

- 稀疏向量持久化并改为倒排检索，实现稳定 ID 和增量索引。
- 完成 CPU/GPU 环境拆分、依赖锁定、容器化与 readiness/liveness。
- 做端到端并发压测，按结果拆分索引任务、OCR、推理和 API 服务。
- 增加用户/租户、会话生命周期、数据脱敏与审计能力。

## 5. 建议持续跟踪的核心指标

| 维度 | 指标 |
|---|---|
| 数据质量 | 文件解析成功率、空文本率、OCR 告警率、可定位来源占比 |
| FAQ | 命中率、Precision、Recall、误命中率 |
| 路由 | domain 准确率、strategy 准确率/实际收益 |
| 检索 | Recall@K、MRR、nDCG、无结果率、source filter 正确率 |
| 生成 | 答案正确性、忠实度、引用正确率、拒答准确率 |
| 性能 | 冷启动、首 token、端到端 P50/P95/P99、各阶段耗时 |
| 稳定性 | HTTP/SSE 错误率、LLM 超时/限流率、MySQL/Chroma 错误率 |
| 成本 | 每问 token、LLM 调用次数、摘要调用次数、CPU/GPU 利用率 |
| 运维 | 索引构建时长、构建失败率、回滚成功率、活动索引版本 |

## 6. 最容易被低估的三个难点

1. **RAG 的答案问题通常不是生成模型单点问题。** 文档解析、切分、召回、重排和 Prompt 任一阶段都可能造成最终错误，因此必须保留中间证据并分层评估。
2. **“全量重建能跑通”不等于“索引可运营”。** 真正上线需要版本、原子切换、增量更新、失败回滚、状态查询和多实例一致性。
3. **多轮历史不是简单拼接。** 它涉及会话隔离、并发顺序、摘要版本、成本上限、隐私保留和失败恢复；当前后台线程方案适合演示，但需要任务化后才能稳定承载真实用户。

## 7. 结论

当前项目功能链路完整，适合作为领域 RAG 原型和效果验证平台；距离稳定生产化的主要差距集中在：**安全、索引原子性、数据质量、并发控制、评估闭环和可观测性**。建议先处理两个 P0 问题，再以自动化测试和分层评估作为后续检索优化、性能优化的基础。否则继续叠加模型和策略，短期可能提升个别示例效果，却会让回归定位和线上稳定性越来越困难。
