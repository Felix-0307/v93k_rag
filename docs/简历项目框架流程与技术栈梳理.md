# V93K RAG 问答项目框架流程与技术栈详解

> 本文只讨论简历中的“V93K 半导体测试知识智能问答系统”及当前仓库能核对的 RAG 实现。简历项目的历史数据和成果属于简历陈述；当前仓库默认运行的是由原有 RAG 链路改造的 SemiconRAG 教学原型。两者使用相近技术，但知识资料、路由领域和验证结果不能混用。

## 1. 先用一句话理解这个项目

**用户问测试知识问题时，系统先从手册等资料里找证据，再让大模型根据证据回答，并把来源返回给用户。** 这就是 RAG（检索增强生成）：`检索 Retrieval → 组织上下文 → 生成 Generation`。可以把它理解为“先翻书，再作答”。

简历中的资料范围包括 V93K 手册、常见错误、STIL 语法和测试 API。它要解决的不是让大模型背下所有手册，而是让它在每次回答前拿到可能相关的原文。这样错误码、API 名称等细节更容易查到，也方便检查答案依据。

## 2. 整体框架：两条链路

```text
离线建库（资料更新时运行）
原始文档 → 文本解析/OCR → 元数据 → 父子块切分 → BGE-M3 编码
                                              ├→ Chroma 子块稠密向量
                                              ├→ Chroma 父块原文
                                              └→ 内存稀疏索引

在线问答（每次提问运行）
问题 → FAQ 前置匹配 ──命中→ 标准答案
             ↓未命中
      意图/领域/策略路由 → 查询改写 → 稠密+稀疏召回 → RRF 融合
                                                       ↓
      返回答案与来源 ← LLM 根据资料生成 ← 父块恢复/重排
             ↓
      MySQL 保存问答；较早历史压缩成摘要
```

**离线**是提前把资料整理成“能搜索的目录”，不需要每来一个问题就重新读完所有 PDF。**在线**是用户真正提问时，根据问题找到少量相关资料，再组织答案。当前主要入口分别是 [`scripts/build_index.py`](../scripts/build_index.py) 和 [`api/routes.py`](../api/routes.py)。

## 3. 离线建库：资料如何变成索引

### 3.1 加载文档和 OCR

当前加载器支持 PDF、DOCX、PPT/PPTX、图片、Markdown 和 TXT。普通文本直接提取；扫描页或图片需要 OCR 把图上的字识别出来。PDF 加载器先用 PyMuPDF 取文本层，对满足大小阈值的嵌入图片再调用 RapidOCR。系统会为文档保留来源文件名、文件路径等元数据；当前 SemiconRAG 还根据文件所在目录打上五类领域标签。

**通俗地说：**原始文件可能是“书、照片、演示文稿”，检索器只认文本，所以第一步是把它们都变成文字，并记住文字从哪里来。OCR 可能把 `0/O`、`1/I`、单位或错误码认错，关键资料入库前仍要人工抽查。当前实现按文件名和目录处理同名资料，不能把它理解为完善的文档版本管理。

代码位置：[`rag_qa/core/document_processor.py`](../rag_qa/core/document_processor.py)、[`rag_qa/loaders/`](../rag_qa/loaders/__init__.py)。

### 3.2 父子块切分

文档通常太长，无法整篇塞进模型；只切成很短的段又容易丢掉前后条件。因此系统切两层：

| 层级 | 当前配置 | 主要用途 |
| --- | --- | --- |
| 父块 | 约 1200 **字符** | 保留一段较完整的上下文，最终交给生成模型阅读。 |
| 子块 | 约 300 **字符**，重叠 50 字符 | 用较小粒度定位具体术语、错误码和句子。 |

子块带 `parent_id`。搜索先找到子块，然后按这个 ID 取回对应的父块。**子块像目录索引，父块像实际要阅读的那一页。** 重叠 50 字符用于减少一句话刚好被切开时的信息损失；代价是相邻块会有少量重复。当前切分器优先尝试段落、换行、句末标点等中文边界。这里的 1200/300/50 是字符数，不是 token 数。

代码位置：[`rag_qa/splitters/chinese_recursive_splitter.py`](../rag_qa/splitters/chinese_recursive_splitter.py)、[`rag_qa/core/document_processor.py`](../rag_qa/core/document_processor.py)、[`config.ini`](../config.ini)。

### 3.3 BGE-M3 同时做两种表示

系统通过 FlagEmbedding 加载本地 BGE-M3。它对每个子块生成两类检索表示：

- **稠密向量**：把整段语义压成一串数字。问法不同但意思相近，也可能靠近，例如“测试程序调用失败”和“API 执行报错”。
- **稀疏词项权重**：记录哪些原词或词片重要。对 `STIL`、错误码、API 名这类必须精确匹配的内容很有帮助。

两个表示互补。当前代码分别调用 `encode_dense` 和 `encode_sparse`；稀疏部分是 BGE-M3 的 `lexical_weights`，**不是 BM25**。BGE-M3 负责“把文本变成可比较的表示”，不负责生成最终回答。代码位置：[`rag_qa/core/embedding.py`](../rag_qa/core/embedding.py)。

### 3.4 数据到底存在哪里

当前仓库用两个 Chroma collection：

| 存储位置 | 存什么 | 为什么 |
| --- | --- | --- |
| 子块 collection | 子块文字、稠密向量、`parent_id`、`source`、`area` 等 | 支持向量检索，并能找到对应父块。 |
| 父块 collection | 父块原文与来源 | 命中子块后按 ID 还原完整上下文；父块不参与向量搜索。 |
| 进程内稀疏索引 | 每个子块的词项权重 | 完成另一条词项检索路；服务重启后从已存子块重新计算。 |

简历技术栈写的是 **ChromaDB**，当前代码也确实使用 Chroma；不要把依赖列表里出现的 Milvus 或 FAISS 等同于当前链路正在使用它们。当前 `config.ini` 的两个集合名为 `semicon_kb` 和 `semicon_kb_parents`，对应教学原型，不是简历时期 V93K 的集合名。

建库脚本会全量清空当前两个集合后重建。它适合小规模原型，但资料很多或在线服务持续运行时，重建期间可能影响查询，应改成新索引构建完成后再切换。代码位置：[`rag_qa/core/vector_store.py`](../rag_qa/core/vector_store.py)。

## 4. 在线问答：一个问题如何走完整条链

### 4.1 接口接收问题

前端向 `POST /api/ask` 提交 `question`，可选传入 `source_filter`、`session_id` 和 `stream`。Pydantic 校验请求字段；没有会话 ID 时后端生成一个。普通请求返回 JSON，`stream=true` 返回 SSE 事件。主调度类是 [`RAGSystem`](../rag_qa/core/rag_system.py)，它把 FAQ、路由、检索、生成和会话保存串起来。

`source_filter` 是按文件 stem 精确限定来源，例如只查某一份资料；传了它时，知识库检索以来源过滤为主，不再使用自动路由出的领域过滤。它还会限制可匹配的 FAQ 来源。

### 4.2 FAQ 为什么放在最前面

高频且答案稳定的问题可以预先写成标准问答。当前 FAQ 独立保存在 JSON 中，启动或重载时先把标准问题转成向量；提问时与用户问题算余弦相似度。当前阈值是 **0.85**：达到阈值就直接返回标准答案及来源，跳过 LLM 路由、知识库检索、重排和生成。它像一个“相似问题快速通道”，但不是键值完全相等的缓存。

阈值太低可能误命中，太高又可能漏掉同义问法；0.85 是当前配置值，不能直接说已在真实业务数据上完成标定。修改 FAQ 后调用 `/api/faq/reload`，无需重建文档索引。代码位置：[`rag_qa/core/faq_store.py`](../rag_qa/core/faq_store.py)。

### 4.3 FAQ 未命中后怎样路由

路由器调用一次大模型，请它返回三个判断：

1. **domain**：是知识问答 `knowledge`，还是闲聊 `chitchat`。闲聊不走知识库检索。
2. **area**：当前教学原型属于工艺、设备、良率、洁净室、质量中的哪一类，供检索时过滤资料。
3. **strategy**：选 Direct、HyDE、SubQuery、Backtracking 哪种检索方式。

服务端对输出做枚举校验，避免模型写出不存在的策略或领域。解析或调用失败时，当前代码回退到 `knowledge + process + direct`。这能让流程继续运行，但回退的 `process` 领域也可能使真实问题查不到资料，所以它是可用性兜底，不代表分类一定正确。简历时期的 V93K 问答不应被描述成天然具有当前教学原型的五领域路由。代码位置：[`rag_qa/core/query_router.py`](../rag_qa/core/query_router.py)。

### 4.4 四种检索策略分别做什么

| 策略 | 具体动作 | 适用问题 | 要注意什么 |
| --- | --- | --- | --- |
| Direct | 原问题直接检索 | “某错误码是什么意思？”这类明确问题 | 调用少、链路短；问题表述过于含糊时可能漏召回。 |
| HyDE | 先由 LLM 生成一段假设性回答，再用它检索 | “如何系统排查某类故障？”这类宽泛问题 | 假设文本只是检索线索，不能直接当事实或最终答案。 |
| SubQuery | 把问题拆成多个独立子问题，逐个检索后合并 | 同时涉及设备、程序和数据的多因素问题 | 召回更全，但 LLM 和检索调用增加，耗时也会增加。当前最多取 4 个子问题。 |
| Backtracking | 把当前问题改写得更独立、更可检索 | “那这个参数呢？”之类追问 | 当前改写函数只收到本轮问题，没有稳定注入历史，因此不能声称已经完整解决指代消解。 |

策略由路由器选择，检索器负责执行；生成策略文本的 LLM 调用失败时会退回原问题。代码位置：[`rag_qa/core/retriever.py`](../rag_qa/core/retriever.py)、[`rag_qa/core/prompts.py`](../rag_qa/core/prompts.py)。

### 4.5 稠密召回、稀疏召回与 RRF 融合

每个检索问题都走两条路：

- **稠密路**：BGE-M3 将问题转向量，在 Chroma 子块 collection 中找语义接近的子块。
- **稀疏路**：BGE-M3 给问题生成词项权重，在进程内索引里找重要词项匹配的子块。

两路原始分数的含义不同，不能简单相加。RRF（倒数排名融合）只看“各自在第几名”：当前代码按 `1 / (60 + 排名)` 给每条路的排名贡献，再对同一子块求和。比如某子块稠密第 2、稀疏第 3，会得到两次贡献；另一子块只在稠密第 1，只得到一次贡献。这样兼顾语义近似和准确术语。当前每条检索问题默认取最多 **5** 个融合后的子块，SubQuery 会把多次结果按子块 ID 合并去重。

注意：当前稀疏索引放在内存，启动时需要根据 Chroma 中的子块重新编码恢复。资料规模增长后，它的启动耗时和查询开销都需要重新评估。代码位置：[`rag_qa/core/vector_store.py`](../rag_qa/core/vector_store.py)。

### 4.6 恢复父块和精排

命中的子块可能只包含半句话或一个小段。系统根据 `parent_id` 批量取回父块，对重复父块去重，再视配置调用 BGE-Reranker-Large。Reranker 是 CrossEncoder：它同时阅读“用户原问题 + 候选父块”，给每个候选打相关性分数。最后最多保留 **3** 个父块作为生成上下文。

可以把两段检索理解为：**BGE-M3 先快速海选，CrossEncoder 再仔细复试。** 精排通常更耗时，因此只对少量候选执行；当配置关闭或候选过少时，代码直接截取候选。当前配置启用重排，但实际运行还要求本地模型路径和权重可用。代码位置：[`rag_qa/core/reranker.py`](../rag_qa/core/reranker.py)。

### 4.7 生成答案、来源与拒答

系统把父块拼成带 `[资料来源: ...]` 标签的上下文，再把用户问题交给 LLM。提示词要求依据上下文回答，缺证据时说明“根据当前知识库，信息不足”，并引用资料标题。若完全没有恢复出父块，代码直接返回知识库内容不足的提示，不再让 LLM 凭空回答。

当前 `config.ini` 配置的生成模型是 `glm-4.5-air`，通过 OpenAI 兼容协议调用；OpenAI SDK 是**调用接口的客户端**，不表示底层使用 OpenAI 模型。当前来源主要是文件标题或 stem，不是可点击的精确页码、段落定位；提示词能降低幻觉风险，但不能保证模型每句话都严格有据。代码位置：[`rag_qa/core/generator.py`](../rag_qa/core/generator.py)、[`rag_qa/core/llm_client.py`](../rag_qa/core/llm_client.py)、[`rag_qa/core/prompts.py`](../rag_qa/core/prompts.py)。

### 4.8 多轮会话和 SSE 怎样工作

MySQL 的 `sessions` 表保存每轮问题、回答、路由、来源和耗时；`summaries` 表保存较早对话的压缩摘要。生成时读取“**旧摘要 + 最近 3 轮原文 + 本轮问题 + 本轮检索资料**”。这是在上下文长度与追问连续性之间做折中。回答结束后同步保存本轮，非 FAQ 路径再用后台线程更新摘要。

当前历史主要用于答案生成，检索器没有完整利用它来消解“它”“那个错误”一类代词；同一会话快速并发请求时，后台摘要也可能相互覆盖。MySQL 记录是会话功能，Chroma 保存的是知识文档，两者职责不同。代码位置：[`rag_qa/chat_history.py`](../rag_qa/chat_history.py)、[`rag_qa/core/rag_system.py`](../rag_qa/core/rag_system.py)。

`stream=true` 时，FastAPI 以 SSE 逐条发出 `meta`、`chunk`、`done` 事件。`meta` 告诉前端路由和会话 ID，`chunk` 是正在生成的文本，`done` 包含来源和耗时。浏览器用 `fetch` 读取响应流并逐段显示。**SSE 是服务端向浏览器持续推送，不是 WebSocket 双向连接。**代码位置：[`api/routes.py`](../api/routes.py)、[`web_ui/dist/index.html`](../web_ui/dist/index.html)。

## 5. 技术栈速查：每个组件到底负责什么

| 技术 | 职责 | 它解决的具体问题 |
| --- | --- | --- |
| Python | 业务编排语言 | 把加载、建库、检索、生成和服务代码连成一条链。 |
| FastAPI / Pydantic | 对外接口与参数校验 | 接收问题、返回普通 JSON 或 SSE；约束输入输出字段。 |
| LangChain 基础组件 | 文档和提示词表示 | `Document` 保存正文与元数据，文本切分器处理段落，`PromptTemplate` 集中管理提示词。在线主链由项目自写类编排。 |
| PyMuPDF / RapidOCR | 文档解析 | 从 PDF 文本层或图片中取出可检索的文字。 |
| BGE-M3 / FlagEmbedding | 子块和问题编码 | 同时服务语义检索与词项检索。 |
| ChromaDB | 持久化和稠密召回 | 保存子块向量、元数据及父块原文；当前是两个 collection。 |
| 内存稀疏索引 | 词项召回 | 保存 BGE-M3 的 lexical weights，补强错误码、API 名等精确术语匹配。 |
| RRF | 结果融合 | 按排名合并稠密、稀疏两条结果。 |
| BGE-Reranker-Large | 候选精排 | 对问题和父块成对评分，减少无关上下文。 |
| LLM 兼容 API | 路由、查询改写、生成、摘要 | 做需要语言理解和表达的环节；最终答案仍要受检索资料约束。 |
| MySQL / PyMySQL | 会话存储 | 保存逐轮问答和摘要，不存文档向量。 |
| RAGAS | 离线评估 | 看检索上下文是否相关、是否覆盖应找到的证据。 |
| 原生 HTML/JavaScript、Tailwind CSS | 当前演示页面 | 发起 API 请求、展示流式文字、记录会话 ID 和构建样式。 |

## 6. 用两个例子串起链路

### 6.1 按简历 V93K 场景理解

假设工程师问：“某个 V93K 错误码在测试程序里是什么意思？”系统应先在 FAQ 中找标准问答；未命中再到 V93K 错误说明、手册和 API 资料里检索。错误码原词更依赖稀疏召回，同义解释更依赖稠密召回；融合后恢复父块，重排，再让 LLM 根据手册原文解释并列出来源。**这是按简历项目和 RAG 方法描述的示例，不代表当前默认配置会查询 V93K 资料。**

### 6.2 按当前仓库默认场景理解

用户问：“刻蚀腔体 particle 超标怎么排查？”FAQ 若未命中，路由器可能选 `equipment + subquery`，把设备维护、最近 PM、量测等拆开搜索；两路召回和重排后，LLM 根据现有演示资料回答。路由结果由模型生成，不能保证每次都选同一策略。缺设备型号或受控 PM 文档时，回答应说明缺少证据，不能编造实际操作参数。

## 7. 评估、结果和应怎样理解简历数字

简历写到：V93K 项目覆盖四类资料，形成 **25 个父块、120 个子块**；FAQ 前置使高频标准问题可跳过后续链路；Direct 链路冒烟样本单题约 **6～9 秒**。这些是简历中的 V93K 项目口径，当前 SemiconRAG 默认目录、资料规模和模型配置已经不同，不能直接用当前教学原型复现这些数字。FAQ “省去调用”是链路结构能够支持的结论；具体节省多少时间和费用还需要基于真实问题分布与命中率统计。

当前仓库的评估脚本默认读取 `data/eval/semicon_qa_v1.json`，对每题固定走 **Direct 检索 + 生成**，然后用 RAGAS 计算 `context_precision`（检索到的内容有多相关）与 `context_recall`（该找到的证据覆盖得如何）。脚本里所谓综合分只是这两项的均值；它不等于答案准确率，也没有完整覆盖 FAQ 命中率、路由选择、多轮追问或四种策略的对比。代码位置：[`scripts/run_eval.py`](../scripts/run_eval.py)、[`rag_qa/eval/runner.py`](../rag_qa/eval/runner.py)。

若要系统评估，应把问题按“标准 FAQ、错误码精确词、语义改写、多因素问题、多轮追问、无答案问题”分组，并分别记录：FAQ 误命中与漏命中、子块/父块召回、来源是否正确、答案是否有据、端到端耗时。这样才能知道问题发生在解析、召回、重排、生成还是会话环节。

## 8. 当前仓库与简历的对应边界

- **能从当前代码看到的：**多格式加载与 OCR、父子块、BGE-M3 稠密/稀疏双路、RRF、Chroma 双 collection、FAQ 前置、四种检索策略、可选 CrossEncoder 重排、FastAPI/SSE、MySQL 会话及 RAGAS 上下文指标。

## 9. 代码阅读顺序与运行顺序

**理解代码时**，先看 [`README.md`](../README.md) 和 [`config.ini`](../config.ini) 确认当前场景；然后看 `document_processor.py → embedding.py → vector_store.py` 理解建库，再看 `faq_store.py → query_router.py → retriever.py → rag_system.py → generator.py` 理解问答，最后看 `api/routes.py`、`chat_history.py` 和评估脚本。`config.ini` 含敏感配置，分享资料时不要复制其中凭据。

**运行当前教学原型时**，按仓库说明准备依赖、本地模型权重、LLM 接口与 MySQL；执行 `python scripts/build_index.py`；再执行 `python -m uvicorn main:app --host 127.0.0.1 --port 8000`。改文档后重建索引，改 FAQ 后调用 `/api/faq/reload`。这些步骤启动的是当前 SemiconRAG 默认资料；要复现 V93K 项目，必须另行确认当时的数据目录、集合配置、模型和评估集。
