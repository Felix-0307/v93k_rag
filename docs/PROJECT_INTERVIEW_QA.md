# V93K RAG 项目难点：面试问答与追问稿

> 使用方式：不要整段背诵。先用“30 秒回答”概括，面试官对哪一点感兴趣，再展开对应追问。  
> 口径说明：文中把内容分成“项目已实现”和“当前仍可优化”，避免把尚未落地的方案说成已经完成。

## 一、开场：面试官问“介绍一下这个项目”

### 面试官：简单介绍一下你的项目。

**30 秒回答：**

我做的是一个面向 V93000 半导体测试机资料的 RAG 知识问答系统。它支持 PDF、Word、PPT、Markdown 和图片等多种资料，入库时会做 OCR、父子分块，并使用 BGE-M3 生成稠密向量和稀疏词项权重。在线问答时先匹配 FAQ，未命中再通过 LLM 判断问题类型和检索策略，然后进行稠密与稀疏混合检索、父块还原和 BGE Reranker 重排，最后调用大模型生成回答。系统还实现了 SSE 流式输出、MySQL 多轮会话历史和 RAGAS 离线评估。

### 面试官：这个项目和普通的“向量库加大模型”有什么区别？

**参考回答：**

主要有四点区别。

第一，数据不是只有干净文本，还包括扫描 PDF、图片、表格和中英文专业术语，所以增加了多格式解析和 OCR。第二，检索不是只用稠密向量，而是 BGE-M3 的稠密与稀疏检索结合，通过 RRF 融合后再重排，兼顾语义问题和错误码、API 名称这类精确关键词。第三，采用父子块设计，用小块提高召回精度，再还原大块给模型补充上下文。第四，FAQ 放在最前面，标准问题命中时直接返回标准答案，不再调用路由、重排和生成模型，降低延迟和成本。

## 二、核心问题：项目中最难的地方是什么？

### 面试官：你觉得这个项目最难的地方是什么？

**推荐回答：**

我认为最难的不是把 RAG 链路跑通，而是让检索结果既准确又稳定。V93K 资料里既有概念性描述，也有错误码、API、STIL 语法和操作步骤。只做语义向量检索时，概念题表现还可以，但精确术语容易召回不准；只做关键词检索，又处理不好用户的自然语言表达。

所以我最终使用 BGE-M3 同时生成稠密向量和稀疏词项权重，两路分别召回后用 RRF 做排名融合，再把命中的子块还原成父块，最后用 BGE Reranker 根据原问题重新排序。这里真正困难的是切分大小、召回数量、父子块关系和重排候选数之间相互影响，需要通过评估集反复调优，而不是只看几个演示问题。

### 面试官追问：为什么要同时用稠密检索和稀疏检索？

**参考回答：**

两者解决的问题不同。稠密检索更擅长语义相似，比如用户问“DPS 是干什么的”，即使原文写的是“Device Power Supply 用于给 DUT 提供可编程电源”，也能匹配。稀疏检索更擅长精确词项，比如错误码、类名、函数名、STIL 关键字，这些内容一两个字符的差异都很重要。

V93K 场景同时存在这两类问题，因此混合检索比单一路径更稳。它不是简单重复检索，而是让两种检索方式互补。

### 面试官追问：两路分数尺度不同，怎么融合？

**参考回答：**

没有直接把余弦相似度和稀疏点积分数相加，因为它们不在同一个量纲。我使用 RRF，也就是 Reciprocal Rank Fusion，只利用每个结果在各自列表中的排名：

```text
score(d) = Σ 1 / (K + rank_i(d))
```

同一个分块如果在稠密和稀疏列表里都排名靠前，会得到两路分数累加；只在某一路命中的结果也可以保留。这样避免了不同模型分数难以校准的问题。

### 面试官追问：为什么 RRF 的 K 取 60？

**稳妥回答：**

当前实现使用了 RRF 中常见的经验值 60，目的是降低第一名和后续名次之间过大的分数差距，让两路结果都有融合机会。但我不会说 60 一定是最优值。更严谨的做法是把它和 top-k、rerank 候选数一起，通过固定评估集做参数实验，再根据 Recall@K、MRR 或 nDCG 选择。

### 面试官追问：为什么还要加 Reranker？向量检索不够吗？

**参考回答：**

向量检索适合从大量数据中快速筛选候选，但它通常分别编码问题和文档，交互不够充分。CrossEncoder Reranker 会把“问题和候选文档”成对输入模型，可以更细致地判断相关性，不过计算成本更高。

所以我的设计是先用混合检索缩小候选范围，再只对还原后的少量父块做重排。这样把召回效率和排序精度分开处理，不会让 Reranker 扫描整个知识库。

### 面试官追问：Reranker 能解决召回不到的问题吗？

**参考回答：**

不能。Reranker 只能重新排列已经召回的候选，召回阶段完全漏掉的文档无法被它补回来。因此评估时要先关注 Recall@K，再看重排后的 MRR、nDCG 或上下文精确度。召回不足时应该调整数据解析、分块、查询改写或混合检索，而不是盲目调 Reranker。

### 容易踩坑

- 不要回答“加了 Reranker，所以准确率一定更高”，应说明它只能改善候选排序。
- 不要声称 `RRF_K=60` 已被证明最优；当前属于经验参数。
- 不要只说“用了混合检索”，要讲清楚两路检索分别解决什么问题，以及为什么不能直接加原始分数。

## 三、父子分块为什么是难点？

### 面试官：为什么不直接把文档切成固定大小的块？

**推荐回答：**

固定小块有利于精确召回，但容易把一个完整步骤、表格或概念说明切断；固定大块上下文完整，但会混入较多无关信息，Embedding 表达也不够聚焦。

所以项目采用父子块：父块大约 1200 字符，保存完整上下文；再从父块切出大约 300 字符的子块用于检索。命中子块后，根据 `parent_id` 去重并还原父块，把父块交给 Reranker 和生成模型。这样小块负责“找得准”，父块负责“回答时看得全”。

### 面试官追问：父子块方案有什么副作用？

**参考回答：**

首先，多个高分子块可能属于同一个父块，如果不按 `parent_id` 去重，会浪费上下文窗口。其次，父块还原后文本变长，重排和生成成本会上升。第三，如果父块边界本身切错了，还原也无法恢复跨父块的上下文。因此父块、子块和 overlap 需要联合调优。

### 面试官追问：为什么父块 1200、子块 300、重叠 50？

**稳妥回答：**

这是当前项目的初始经验配置，不是理论最优值。选择时考虑了中文技术文档中一段完整说明的长度，以及 BGE-M3 的最大输入长度。实际优化应该按文档类型分桶测试，例如 API 文档可能适合按函数或标题切分，故障排查文档适合按问题与解决步骤切分，而不是所有文档永久共用同一组字符数参数。

### 面试官追问：如果表格被切断怎么办？

**参考回答：**

理想做法是在解析阶段保留表格和标题结构，优先进行结构化切分，而不是先压平再按字符切。可以把一行或一个完整表格作为不可拆分单元，并把标题路径、页码、表格编号写入 metadata。当前项目已经能提取部分表格文本，但结构保持和按类型切分仍是下一步重点。

### 容易踩坑

- 不要把字符数参数说成模型的 token 数。
- 不要只讲父子块优点，也要说明去重、上下文膨胀和边界问题。
- 当前 ID 包含文档遍历序号，尚未实现基于内容哈希的稳定增量索引，不要说已经支持完善的增量更新。

## 四、多格式解析和 OCR 会被怎么追问？

### 面试官：文档入库最大的困难是什么？

**推荐回答：**

最大的困难是输入数据质量不统一。项目资料不仅有 Markdown 和带文本层的 PDF，还有扫描 PDF、Word、PPT、图片、表格和截图。RAG 后面的检索和生成做得再好，如果前面漏字或结构丢失，也不可能得到正确答案。

因此我为不同文件类型设计了独立加载器：文本层优先直接提取，图片内容再调用 RapidOCR；统一补充 `source`、`file_path` 等 metadata，然后进入父子分块。开发中需要重点处理空文本、重复文档、图片 OCR、表格顺序和单文件失败等边界情况。

### 面试官追问：为什么选择 RapidOCR？

**参考回答：**

这个项目首先考虑本地可部署和 CPU 可运行，因此使用 `rapidocr_onnxruntime`，不强依赖 GPU，也不需要把内部文档上传给第三方 OCR 服务。它的代价是复杂表格、低清截图和特殊符号的识别质量仍需要通过预处理和样例评估改进。

### 面试官追问：如何判断一个 PDF 是否需要 OCR？

**参考回答：**

项目当前先提取 PDF 文本层，同时对页面中面积达到阈值的大图做 OCR，以避免 logo、水印等小图片带来大量噪声。但单纯按图片面积并不完美，小图也可能包含关键错误码，扫描页也可能有特殊编码方式。

更完整的策略应该结合页面文本字符数、图片覆盖比例和 OCR 置信度：文本很少且图片覆盖大时整页 OCR；文本层充足时只处理关键图片；最终记录每页采用了哪条路径。

### 面试官追问：OCR 错一个字符会有什么影响？

**参考回答：**

对普通描述可能只是轻微语义噪声，但对错误码、API 名和引脚名影响很大，因为这些内容依赖精确匹配。我的思路是保留文本层和 OCR 原文、对关键术语做规则校验或词典纠错，并用专门包含错误码和 API 名的测试集验证召回，而不是只用整体字符识别率判断。

### 面试官追问：怎么保证文档没有漏入库？

**参考回答：**

不能只以接口返回成功作为依据。应该生成构建清单，逐文件记录文件哈希、页数、字符数、分块数、OCR 页数、异常和空文本率，并把“解析失败、空文本、分块数异常”作为构建失败或告警条件。当前代码会记录加载日志并跳过失败文件，但完整的构建质量报告仍是需要补强的部分。

### 容易踩坑

- 不要说“支持 PDF 就等于支持所有 PDF”。文本 PDF、扫描 PDF、混合 PDF 是不同问题。
- 当前 PDF 图片字节解码路径存在改进空间，不要声称 OCR 已覆盖全部边界情况。
- 项目目前以文件 stem 去重，同名不同目录文件可能被误判重复，这是可以主动说明的优化点。

## 五、FAQ 和查询路由为什么放在检索前？

### 面试官：为什么要单独做 FAQ？直接走 RAG 不行吗？

**推荐回答：**

可以直接走 RAG，但对高频、答案固定的问题没有必要。FAQ 使用本地 BGE-M3 编码标准问题，余弦相似度达到阈值后直接返回人工维护的标准答案。这样跳过意图识别、查询改写、检索、重排和生成模型，答案更稳定，延迟和 LLM 成本也更低。

如果 FAQ 未命中，才让 QueryRouter 判断是知识问题还是闲聊；知识问题再选择 direct、HyDE、subquery 或 backtracking 检索策略。

### 面试官追问：FAQ 为什么不用关键词完全匹配？

**参考回答：**

用户不会总是按标准问题原样提问。例如“DPS 板卡有什么用”和“Device Power Supply 的作用”表达不同但语义一致。向量匹配可以覆盖改写和近义表达。为了防止误命中，需要准备 FAQ 正例和相似负例，对阈值做标定。

### 面试官追问：阈值 0.85 是怎么来的？

**稳妥回答：**

0.85 是当前初始经验值，选择时偏保守，因为 FAQ 一旦误命中会直接返回固定答案，风险比 FAQ 漏掉后继续走 RAG 更大。严谨做法是收集每条 FAQ 的多种问法，以及语义相近但答案不同的 hard negative，统计不同阈值下的 precision、recall，优先保证 precision，再确定阈值。

### 面试官追问：为什么路由要用 LLM？规则不行吗？

**参考回答：**

规则对错误码、明确关键词很有效，而且便宜、稳定；但自然语言问题可能很模糊，例如“这个怎么配”需要结合表达判断意图。项目当前用一次 LLM 调用同时完成 domain 分类和 strategy 选择，并校验输出是否属于允许集合，异常时降级成 `knowledge + direct`。

进一步优化可以采用“高置信规则优先、轻量分类器或 LLM 兜底”，减少每个 FAQ miss 都调用大模型的成本。

### 面试官追问：HyDE、subquery、backtracking 分别适合什么问题？

**参考回答：**

- `direct`：问题清晰、术语明确，直接检索即可。
- `HyDE`：用户问题短或抽象，先生成一段假设答案，再用答案式表达检索相关文档。
- `subquery`：一个问题包含多个方面，拆成多个子问题分别召回再合并。
- `backtracking`：问题过于具体或带有错误前提时，先抽象成更基础的问题再检索。

这些策略会增加 LLM 调用和延迟，所以不能默认全部执行，必须看它们在分类评估集上的实际收益。

### 容易踩坑

- 不要说 FAQ 命中率越高越好，误命中比漏命中更危险。
- 不要说四种策略一定比 direct 好；复杂策略可能引入错误改写。
- 当前路由依赖远程 LLM，应主动提到失败时降级到 direct。

## 六、多轮会话历史的难点是什么？

### 面试官：你是怎么实现多轮对话的？

**推荐回答：**

每次一问一答会同步写入 MySQL 的 `sessions` 表。生成下一轮回答时，取最近 3 轮原始对话，再拼接更早内容的摘要。这样近期信息保持原文，较早信息经过压缩，避免上下文随着轮数无限增长。

当前轮写库成功后，非 FAQ 路径会启动后台线程调用 LLM 更新摘要，减少用户等待时间。FAQ 命中只保存问答，不立即调用摘要模型，后续普通问题更新摘要时再纳入。

### 面试官追问：为什么最近保留 3 轮？

**稳妥回答：**

3 轮是当前在上下文完整性与 token 成本之间的经验折中，不是固定真理。太少可能丢失代词和连续追问关系，太多会增加 Prompt 长度、延迟和噪声。应该根据真实会话长度和多轮评估集比较 3、5、8 轮，或者基于相关性动态选择历史。

### 面试官追问：后台线程更新摘要会不会有并发问题？

**推荐回答：**

会，这是当前实现已经识别出的限制。同一 session 快速连续提问时，多个线程可能读到相同旧摘要，后完成的旧任务反而覆盖更新的摘要，产生丢更新。另外每个请求直接创建 daemon 线程也缺少并发上限。

生产化方案是使用有界任务队列，同一 session 串行处理；摘要表增加 `covered_turn_id` 或版本号，更新时做 compare-and-swap，只允许覆盖范围更大的新摘要写入。同时只处理上次摘要之后的增量轮次，避免每次重复总结全部历史。

### 面试官追问：为什么不在请求内同步生成摘要？

**参考回答：**

摘要不是当前回答返回前的强依赖，同步执行会额外增加一次远程 LLM 延迟。放到后台可以降低端到端响应时间。但异步化以后必须补任务可靠性、顺序、重试和优雅退出，所以演示版本用线程实现，生产版本应升级为队列或任务系统。

### 面试官追问：MySQL 挂了会怎么样？

**参考回答：**

当前初始化失败不会阻止 RAG 服务启动，系统希望降级成无历史问答；保存失败也会记录日志并停止摘要任务。但读历史发生在生成链路中，如果数据库不可用仍可能造成请求等待连接超时，因此更好的做法是增加连接池、熔断和明确的“history degraded”状态，让数据库故障时快速跳过历史路径。

### 容易踩坑

- 不要把当前后台线程方案描述为完全并发安全。
- 不要只讲摘要节省 token，也要讲摘要可能失真和版本覆盖。
- `session_id` 目前不是认证凭证，生产环境还需要用户身份和会话所有权校验。

## 七、性能优化会被怎么追问？

### 面试官：这个项目为什么首问比较慢？你做了哪些优化？

**推荐回答：**

延迟主要来自本地模型加载、查询路由与改写、Embedding、混合检索、CrossEncoder 重排、远程 LLM 首 token 和数据库操作。项目在 FastAPI lifespan 中预热 BGE-M3 和 Reranker，并提前初始化 Chroma、FAQ 和会话历史，避免把模型冷启动全部压到第一个请求上。

另外增加 FAQ 前置路径，命中后跳过所有远程 LLM 和重排；回答使用 SSE 流式输出，虽然不一定降低总耗时，但能明显降低用户感知的首字等待时间。

### 面试官追问：SSE 和 WebSocket 为什么选 SSE？

**参考回答：**

这个场景主要是服务端持续向客户端发送文本 token，通信方向基本是单向的。SSE 基于普通 HTTP，实现和调试更简单，也适合通过反向代理。WebSocket 更适合高频双向通信。需要注意 SSE 的客户端断开检测、代理缓冲、超时和错误事件协议。

### 面试官追问：目前最大的性能瓶颈在哪里？

**参考回答：**

在当前 CPU 配置下，本地 BGE-M3、CrossEncoder 和稀疏检索都会竞争 CPU；远程 LLM 又决定生成阶段延迟。随着知识库扩大，还有两个明显瓶颈：服务启动时会从 Chroma 读取所有子块并重新计算稀疏权重；查询时稀疏索引会对查询 token 遍历文档权重，规模增长后近似线性变慢。

下一步应先做分阶段埋点和压测，再决定是持久化稀疏权重、改倒排索引、批处理、缓存，还是把 Embedding/Rerank 拆成独立服务。

### 面试官追问：为什么不直接开多个 Uvicorn worker？

**参考回答：**

因为每个进程都会各自加载 Embedding、Reranker 和内存稀疏索引，多 worker 会显著增加内存占用，也可能同时访问本地 Chroma。是否扩 worker 需要根据模型内存、Chroma 并发方式和压测结果决定。更合理的架构可能是 API 层多 worker，而模型推理集中成单独服务进行批处理和限流。

### 面试官追问：流式输出真的更快吗？

**参考回答：**

它主要优化的是感知延迟和首 token 时间，不一定减少模型完成整段回答的总时间。面试中应该分别看 TTFT、总耗时和吞吐，不能只说“用了流式所以性能更好”。

### 容易踩坑

- 不要只给出总耗时，要能拆成路由、检索、重排、首 token、生成、数据库等阶段。
- README 中现有性能数字属于历史数据，不能当成严格压测结果。
- 不要把“预热”说成消除了模型成本，它只是把加载成本从首个请求移到启动阶段。

## 八、索引重建和数据一致性会被怎么追问？

### 面试官：增加或修改文档后怎么更新知识库？

**如实回答：**

当前版本支持全量重建：重新解析 `data/` 下文档、切分并生成向量，然后清空原 collection 再写入。这个方案实现简单，适合当前小规模原型，但它不是最终的生产方案。

我识别出的主要问题是“先删后建”存在空窗期，如果写入中途失败，旧索引也已经被删除；同时在线查询和重建缺少读写协调。因此生产化时会改成带版本号的双缓冲索引：在新 collection 完整构建，校验文档数、分块数和抽样查询后，再原子切换活动版本，失败则继续使用旧版本。

### 面试官追问：怎么做增量更新？

**参考回答：**

首先为每个文档记录规范化相对路径、内容哈希、更新时间和索引版本。分块 ID 使用“文档稳定 ID + 内容哈希或块序号”，而不是依赖遍历顺序。重建时比较 manifest：新增文件只新增，内容变化只更新对应块，被删除的文件删除对应块。完成后还要同步稀疏索引和父块 collection。

### 面试官追问：怎么保证新索引可用？

**参考回答：**

构建结束不能只检查 collection 不为空。至少要校验文件数、父子块数量、空文本比例、父子引用完整性、向量维度、重复 ID，并跑一组固定冒烟查询。全部通过后才能切换活动版本，同时保留上一个版本用于快速回滚。

### 面试官追问：你已经实现原子切换了吗？

**必须如实回答：**

当前版本还没有，现阶段是全量清空后重建。我已经定位了风险并设计了版本化双缓冲方案，但不能把规划描述成已完成。当前系统更适合单机、小语料和受控维护窗口。

### 容易踩坑

- 这是面试官很容易核实的点，不要把“有重建接口”说成“支持无损在线更新”。
- 当前文档 ID 与遍历序号相关，不是真正稳定 ID。
- 重建接口目前还缺少管理员鉴权，这也是生产化必须优先处理的问题。

## 九、如何回答“你怎么评估 RAG 效果？”

### 面试官：你怎么证明优化是有效的？

**推荐回答：**

项目有一套版本化问答数据集，当前用 RAGAS 计算 `context_precision` 和 `context_recall`。前者观察召回上下文中相关内容的比例，后者观察标准答案所需证据是否被召回。评估报告会保存逐题结果和聚合分数，避免只凭人工看几个案例。

但我也意识到当前评估还不完整：评估运行器固定走 direct 检索，没有完整覆盖线上 FAQ 和 QueryRouter；同时缺少最终答案正确性、忠实度、引用正确率、延迟和成本指标。所以更合理的评估应该分层，而不是只看一个总分。

### 面试官追问：context precision 和 recall 有什么区别？

**参考回答：**

`context recall` 更关注该找到的证据是否找全，低 recall 说明召回阶段漏文档；`context precision` 更关注返回的上下文中有多少真正相关，低 precision 说明噪声太多。调大 top-k 通常可能提升 recall，但也可能降低 precision、增加生成 token，因此两者需要一起看。

### 面试官追问：为什么不能只看答案正确率？

**参考回答：**

答案正确不一定代表检索正确，大模型可能依靠自身知识猜对；答案错误也不一定是生成问题，可能是证据没有召回。分层评估可以定位问题究竟在解析、检索、重排还是生成。对于企业知识库，还要看答案是否忠实于提供的资料以及引用是否正确。

### 面试官追问：RAGAS 由 LLM 打分，结果可靠吗？

**参考回答：**

它适合批量对比趋势，但不能完全替代人工评审。Judge 模型可能有随机性、偏差、限流和版本变化。因此需要固定模型和参数、保存逐题原始结果、重复运行观察方差，并对关键业务题和分数变化大的样本进行人工复核。

### 面试官追问：25 道题够吗？

**参考回答：**

不够覆盖生产场景，只适合早期冒烟和建立初始基线。后续要按概念题、精确错误码、API、步骤题、多文档综合、多轮追问、无答案问题、FAQ hard negative 和 OCR 来源分桶扩充，并单独报告各桶结果。

### 容易踩坑

- 不要把 `ragas_score` 当成完整业务准确率；当前只是两项检索指标的平均。
- 不要说评估已经覆盖线上完整路由，当前 runner 固定使用 direct。
- 不要只汇报平均分，要能分析逐题和分类结果。

## 十、异常处理与降级如何回答？

### 面试官：某一个组件挂了，系统会怎么样？

**推荐回答：**

项目在多个位置做了降级：FAQ 检测失败会继续走普通问答；QueryRouter 异常时回退到 `knowledge + direct`；HyDE、子查询或回溯改写失败时使用原问题；生成失败时返回统一提示；MySQL 初始化失败不会阻止 RAG 主服务启动。

不过降级不能只做到“接口不报错”。当前有些生成异常会被转换成普通回答，HTTP 仍显示成功，这会让监控误判。因此更好的做法是返回机器可识别的 `degraded/error_code`，并在日志和指标中区分正常回答、无知识拒答和组件故障。

### 面试官追问：所有异常都捕获是不是更稳定？

**参考回答：**

不是。捕获异常可以保证局部降级，但过度捕获或直接 `pass` 会隐藏数据损坏。例如 OCR 图片处理失败如果完全吞掉，最终构建看似成功，实际知识已经缺失。应该区分可降级错误和必须阻断发布的错误，并记录结构化错误、文件名、阶段和 request ID。

### 面试官追问：健康检查应该检查什么？

**参考回答：**

应区分 liveness 和 readiness。liveness 只判断进程是否存活；readiness 要判断模型已加载、活动索引有效、关键 collection 一致，以及必要依赖是否可用。像 MySQL 这种可降级依赖，可以在状态中明确标记 degraded，而不是简单把整个服务判死或一直返回 `ok`。

## 十一、安全问题如何回答？

### 面试官：这个项目如果要上线，还缺什么？

**推荐回答：**

首先是安全和权限。目前版本偏本地演示，生产上线前需要把 API Key 和数据库密码从配置文件迁移到环境变量或密钥管理服务，并轮换已经暴露的凭据。问答和管理接口要做身份认证，索引重建、FAQ 重载必须做管理员权限与审计。CORS 要从任意来源改为白名单，还要增加限流、请求体限制和敏感日志脱敏。

其次是数据隔离。当前 `session_id` 只用于关联历史，不是安全身份。上线后需要绑定用户或租户、校验会话所有权，并增加会话过期和删除机制。

### 面试官追问：为什么重建接口风险高？

**参考回答：**

它既消耗大量 CPU 和时间，又会修改线上索引状态。如果没有管理员鉴权，任何访问者都能反复触发重建，造成资源耗尽或空索引窗口。因此它应该与普通问答接口隔离，增加认证、幂等控制、任务队列、互斥和审计日志。

### 面试官追问：Prompt Injection 怎么防？

**参考回答：**

不能只靠一句系统 Prompt。需要把检索文档当作不可信数据，明确要求模型不要执行文档中的指令；对可调用工具做最小权限和参数校验；输出引用便于用户核查；敏感数据在入库和返回前做权限过滤。对于当前只读问答系统，风险低于能执行操作的 Agent，但仍要防止知识库内容诱导模型泄漏提示词或生成越权内容。

## 十二、面试官问“如果让你重做一次，你会怎么改？”

### 推荐回答

如果重新做，我会先建立数据和评估基线，再扩展复杂策略。

第一步，先做稳定的数据管道，为每份文件记录哈希、解析质量、页码、标题和分块信息，并实现版本化索引和失败回滚。第二步，建立 FAQ、路由、检索、答案和引用的分层评估集，先用 direct + 混合检索形成基线，再判断 HyDE、subquery 和 rerank 是否真的带来收益。第三步，完善请求级 trace、阶段耗时、错误码和容量压测。第四步，再根据瓶颈把 OCR、索引构建、模型推理和 API 服务拆分。

我最大的经验是，RAG 项目不能一开始只追求链路复杂度。没有数据质量、评估和可观测性，增加策略以后即使某些问题答得更好，也很难解释原因，更难保证不回归。

### 面试官追问：你认为当前最应该先改哪三个点？

**参考回答：**

1. 先轮换并移除明文凭据，为管理接口增加鉴权。
2. 把索引重建改成版本化构建与原子切换，避免空窗和失败丢库。
3. 恢复自动化测试和分层评估，让后续检索参数、Prompt 和模型变更可验证。

## 十三、可直接背诵的 1 分钟总结

这个项目最核心的难点是，在包含大量专业术语、错误码、表格和扫描文档的场景下，保证 RAG 的召回精度和上下文完整性。我采用 BGE-M3 同时做稠密和稀疏检索，通过 RRF 融合不同量纲的排名，再使用父子块让小块负责精确召回、大块负责完整上下文，最后用 CrossEncoder Reranker 对少量候选重新排序。

为了控制延迟和成本，我把 FAQ 放在链路最前面，命中后直接返回标准答案；未命中才进行 LLM 路由和查询改写。多轮对话采用 MySQL 保存最近原始轮次，并用后台摘要压缩更早历史，前端通过 SSE 降低首字等待。

开发过程中我也识别出几个生产化问题：当前索引重建还不是原子操作，后台摘要线程存在同会话并发覆盖风险，稀疏索引启动时需要全量重算，评估目前主要覆盖 direct 检索。因此下一步重点不是继续堆模型，而是完善索引版本、并发控制、分层评估、自动化测试和可观测性。

## 十四、面试表达原则

### 可以明确说“已经实现”的内容

- 多格式文档加载与本地 OCR。
- BGE-M3 稠密向量和稀疏词项权重。
- RRF 混合检索、父子块还原和 BGE Reranker。
- FAQ 前置匹配及热重载。
- LLM 路由和 direct/HyDE/subquery/backtracking 策略。
- SSE 流式响应。
- MySQL 会话历史、最近 3 轮和后台摘要。
- RAGAS context precision/context recall 评估。
- 启动阶段模型预热和异常降级。

### 应明确说“目前的限制/下一步方案”的内容

- FAQ 阈值尚未经过大规模真实数据标定。
- 现有 25 道评估题只够初始基线。
- 索引目前是清空后全量重建，尚未实现原子切换和完善增量更新。
- 稀疏权重尚未持久化，查询还不是倒排索引实现。
- 后台摘要线程尚未做到同会话严格串行和版本控制。
- 当前配置和管理接口需要进一步安全加固。
- 当前工作区缺少完整自动化测试体系。

### 不建议使用的表达

- “准确率很高”——没有明确数据、数据集和指标时不要泛化。
- “解决了幻觉”——RAG 只能降低幻觉，不能保证消除。
- “支持高并发”——没有压测数据和资源规格时不能下结论。
- “支持增量索引”——当前代码主要是全量重建。
- “置信度很高”——当前前端置信度由耗时推算，不是真实模型置信度。
- “所有文档都能 OCR”——应说明不同格式、质量和边界条件。

## 十五、回答公式

面对任何追问，可以用下面四步组织答案：

```text
业务问题 → 为什么普通方案不够 → 我采用的设计与取舍 → 当前结果及仍可优化点
```

示例：

```text
错误码需要精确匹配（业务问题）
只用语义向量容易召回相似但不同的错误（普通方案不足）
所以增加 BGE-M3 稀疏检索，并与稠密排名做 RRF 融合（设计与取舍）
当前已完成混合检索，下一步用错误码专项集量化 Recall@K（结果与优化）
```

这种表达既能说明你理解问题，也能体现工程判断，同时不会把尚未验证的结果夸大。
