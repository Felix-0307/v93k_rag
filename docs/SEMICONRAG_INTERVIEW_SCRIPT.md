# SemiconRAG 面试逐字稿

> 适用口径：个人/学习项目，基于已有 RAG 代码改造成半导体工艺问答原型。下面的“我做了”指当前代码中能展示的工作；演示资料不是真实晶圆厂数据。按自己的实际参与情况修改第一人称表述。

## 一、开场介绍（约 90 秒）

**面试官：介绍一下你做的这个项目。**

**我：**我做的是 SemiconRAG，一个面向晶圆制造知识查询的 RAG 原型。它主要回答五类问题：工艺整合、设备维护、良率分析、洁净室规范和制程质量控制。比如工艺工程师问曝光剂量偏移要核对什么，设备工程师问刻蚀腔体 particle 超标怎么排查，质量工程师问 SPC OOC 后第一步怎么做。

这个项目的核心考虑是：半导体问题里有很多设备型号、腔体、批次、Recipe 版本和控制规则。直接让大模型回答，容易把通用经验说成某条产线的具体参数，所以我把回答约束为基于检索资料，资料不够就明确说不够，涉及停机、放行、PM 或参数修改时要求核对厂内最新受控文件。

技术流程上，离线将 PDF、Word、PPT、图片和 Markdown 等资料解析、OCR、切成父子块，再用 BGE-M3 建立稠密和稀疏索引。在线提问先查独立 FAQ；没命中就由路由器判断业务领域和 Direct、HyDE、SubQuery、Backtracking 四种检索策略。检索阶段融合稠密和稀疏结果，恢复父块，可选重排，然后把上下文交给生成模型。服务用 FastAPI 提供普通问答和 SSE 流式回答，MySQL 保存会话。

目前它是教学原型：默认有五份明确标注为演示的领域资料、三条 FAQ，索引实际建出了六个子块和五个父块。我已经验证过设备和质量领域的检索过滤。它还没有接入晶圆厂真实系统，所以我不会把场景模板里的日请求量、准确率或提效数字说成自己的成果。

## 二、业务和数据

**面试官：为什么要分成这五类知识？**

**我：**因为这五类问题的资料来源和回答方式不同。工艺问题通常要看产品、层次和 Recipe 的适用范围；设备问题要看型号、腔体和 PM 版本；良率问题需要把 WAT、缺陷和工艺履历关联起来；洁净室问题涉及 EHS 和区域规范；质量问题要区分 SPC 控制规则与产品规格。按领域组织后，路由器可以先收窄检索范围，减少把无关资料放进上下文的机会。

**面试官：你们现在的数据从哪里来？**

**我：**当前仓库里的数据是我为演示整理的五份教学文档，分别放在 `process`、`equipment`、`yield`、`cleanroom` 和 `quality` 目录。每份都标了 `DEMO` 文档编号和版本，明确不是生产受控文件。旧项目的 V93K 测试机资料还留作参考，但默认索引目录已经切到新的半导体工艺资料，不会混入问答。真实落地时，首先要取得有权限的 PIMS、EAM、YMS、EHS 等资料，处理脱敏、版本和生效范围，再由领域专家审核。

**面试官：工艺参数表和设备手册怎么切分？**

**我：**现有实现是父子块：较小的子块用于检索，命中后按 `parent_id` 恢复较大的父块给模型，这样既能定位术语，又能保留上下文。资料目录会转成领域元数据，文件名会成为来源标识。对于真正的工艺参数表，通用字符切分还不够，下一步应该按表格、工艺步骤或受控章节切分，并把单位、适用产品、设备和版本作为结构化元数据保存。当前原型还没有完整做到这一点。

## 三、检索链路

**面试官：用户问“刻蚀腔体 particle 超标怎么排查”，系统具体怎么走？**

**我：**先用 BGE-M3 把用户问题编码，与 FAQ 的标准问题做余弦相似度匹配。如果没达到阈值，就让路由器输出 `knowledge`、`equipment` 和一个检索策略。这个问题涉及量测、腔体、最近 PM 和 Recipe 变更等多个方向，预期更适合 SubQuery。检索器把子问题分别检索，再合并去重。底层同时跑 Chroma 稠密检索和 BGE-M3 稀疏词项检索，用 RRF 按排名融合。之后恢复父块，可选 BGE Reranker 重排，最后把带来源标题的资料交给生成模型。回答应该给出排查框架，也要说清楚缺少具体设备型号和受控 PM 文件时不能给出可执行操作。

**面试官：为什么同时用稠密和稀疏检索？**

**我：**稠密向量擅长理解表达不同但语义接近的问题，比如“腔体颗粒异常”和“particle 超标”。稀疏词项更重视原文术语，比如 WAT、OOC、Recipe 名称和设备编号。两种结果用 RRF 融合，不需要直接比较两路分数的尺度。当前稀疏检索来自 BGE-M3 的 lexical weights，是内存索引；我没有把它称为已经实现的 BM25 服务。

**面试官：四种策略分别什么时候用？**

**我：**Direct 用于问题明确、能直接检索的事实题；HyDE 先生成一段假设文本作为检索线索，适合宽泛的研究型问题，但那段假设不能直接当答案；SubQuery 用于多因素问题，拆成互补的检索子问题；Backtracking 用于尝试把复杂或追问式问题改写得更聚焦。策略由一次 LLM 路由调用选择，并校验输出是否在允许集合里；调用失败会退回 `knowledge + process + direct`。目前 Backtracking 的检索改写主要拿到当前问题，尚未稳定注入历史上下文，所以我不会说它已经完整解决了指代消解。

**面试官：FAQ 为什么放在最前面？**

**我：**像“OOC 和 OOS 有什么区别”这种高频且答案相对稳定的问题，可以直接返回经过整理的标准答案，省去路由和生成调用。当前 FAQ 是独立 JSON，只有启用的记录参与匹配，问题向量在加载时预先计算，提问时取余弦相似度最高的一条。阈值目前设为 0.85，只是初始值，还没有用真实正负样本标定，所以不能声称有某个真实缓存命中率。修改 FAQ 后可以调用重载接口，不必重建文档索引。

## 四、可信回答与系统设计

**面试官：怎样防止模型编造工艺参数？**

**我：**首先，默认资料里不放未经核实的生产参数。其次，生成提示词明确要求只根据检索内容回答，缺信息就说“根据当前知识库，信息不足”，不能补造设备规格、控制限或文档版本。第三，检索上下文带来源标题，资料正文也有演示文档编号。对停机、放行、PM 等场景，会提醒以厂内最新受控文件和审批为准。不过我也知道提示词不能保证绝对无幻觉。要用于真实生产，还需要受控文档版本、权限过滤、引用定位、人工审核和专门的错误参数测试集。

**面试官：你用了五个 Milvus Collection 吗？**

**我：**没有。当前实现用的是 Chroma，两个 collection 分别存子块向量和父块原文。五个业务领域通过文件夹和 `area` 元数据标记，在子块检索时过滤。这个方案适合当前小规模原型。要迁移到企业场景，再评估是否按数据规模、权限边界和维护成本拆成多个物理 collection，不能因为模板写了五个就说已经用了五个。

**面试官：流式输出是 WebSocket 吗？**

**我：**当前是 SSE。前端发起 `POST /api/ask`，设置 `stream=true`，后端依次返回路由信息、文本 chunk 和完成事件。问答是服务端持续向浏览器推送，SSE 足够简单；如果以后需要更复杂的双向实时交互，再考虑 WebSocket。

**面试官：多轮会话是怎么做的？**

**我：**会话 ID 由后端生成，前端存在浏览器本地。问答记录写入 MySQL；生成答案时会读取最近几轮和更早的摘要，帮助理解当前问题。摘要在后台线程更新，避免阻塞本轮返回。当前有一个边界：历史主要用于生成阶段，检索查询对“它”“那个腔体”这类指代还不够稳；同一会话快速并发提问时，后台摘要也可能有覆盖风险。这两处需要进一步做历史感知的查询改写和按会话串行更新。

**面试官：开发时遇到过什么实际问题？**

**我：**有一次构建索引时，子块已经写入，但父块写入失败。原因是父块只用于按 ID 取原文，我没有给它传向量，Chroma 就尝试调用默认 embedding 模型并下载权重，环境中的缓存目录没有写权限。定位后我给父块显式传了固定的占位向量，因为父块根本不参与向量检索。再重建索引，确认六个子块和五个父块都写入成功。这个问题让我更注意存储组件的默认行为，也提醒我现在的全量重建仍应改成更安全的版本切换方式。

## 五、效果、边界与收尾

**面试官：项目效果怎么样？准确率是多少？**

**我：**现在不能给出生产准确率。当前只有五条覆盖五个领域的初始教学评估题，未经工艺专家标注。现有 RAGAS 脚本评估的是 Direct 路径的上下文精确度和召回率，不等于端到端回答准确率，也没有覆盖四种策略的实际路由效果。我实际验证了索引构建，以及设备维护和 SPC 质量问题能够命中对应领域资料。下一步会先建立有专家答案、版本和负例的评估集，再分别看路由准确性、检索召回、引用正确性和答案忠实度。

**面试官：如果让你把它做成企业可用版本，优先做什么？**

**我：**第一步是接入有权限的真实资料，把产品、设备、腔体、文档版本、生效时间和权限标签做成结构化元数据，并设计过期文档失效机制。第二步是用专家标注集做基线，尤其关注错误参数和错误版本引用。第三步完善索引原子更新、会话并发和权限隔离。之后再根据真实流量决定缓存、向量库扩容和模型部署方式。当前用的是 GLM 兼容 API，不能声称数据完全不出内网；如果企业有内网要求，要换成经过批准的内部模型端点。

**面试官：一句话说，你在这个项目中最有价值的工作是什么？**

**我：**我把原来偏 V93K 测试机的通用 RAG 链路，改成了按晶圆制造五类业务组织、检索和回答的原型；同时让资料来源、缺证据拒答和真实实现边界都能被检查，而不是只把页面名称换成“半导体工艺”。
