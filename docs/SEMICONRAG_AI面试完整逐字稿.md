# SemiconRAG AI 行业面试逐字稿

## 面试使用说明

这份逐字稿依据当前仓库代码、配置、演示数据和本地索引编写，面向 AI 应用工程、RAG 工程、大模型应用、算法工程和 Python 后端相关岗位。

面试时不需要从头到尾全部讲完。建议先使用一分钟版本回答“介绍一下你的项目”。面试官希望听更多细节时，再切换到五分钟版本。技术面继续追问文档处理、混合检索、重排、查询路由、会话记忆、评估和生产化时，使用十五分钟版本和后面的深挖讲稿。

这份稿子的主体是连续陈述，不是面试问答。每个章节都按照可以直接说出口的方式编写。最后保留少量高频追问，方便面试官打断以后快速回应。

面试表达遵循五个原则。

第一，先讲业务问题和项目目标，再讲技术架构。

第二，先讲为什么这样设计，再讲使用了哪些组件。

第三，明确区分当前已经实现的能力、教学演示数据和未来生产化设计。

第四，不把检索指标说成答案准确率，不把历史项目数据说成当前项目结果。

第五，涉及个人职责、团队规模、开发周期和量化收益时，只使用自己能够证明的事实。

当前项目的准确技术口径如下。

SemiconRAG 是一个半导体工艺知识问答教学原型。默认知识范围包括工艺整合、设备维护、良率分析、洁净室规范和制程质量控制。当前默认数据目录有五份演示文档，独立 FAQ 有三条。物理存储使用两个 Chroma collection，一个保存子块向量，一个保存父块原文。当前本地 SemiconRAG 索引中有六个子块和五个父块。

Embedding 使用本地 BGE-M3。它同时输出一千零二十四维稠密向量和稀疏词项权重。检索阶段执行稠密与稀疏双路召回，再用 RRF 融合排名。候选父块可以使用 BGE Reranker Large 重排。生成和路由调用 GLM 的 OpenAI 兼容接口。服务端使用 FastAPI，流式输出使用 SSE，会话历史使用 MySQL。

当前没有实现五个 Milvus collection、Redis 三级缓存、Qwen 微调、真实生产系统连接、文档级权限隔离、受控文档自动失效和 WebSocket。项目也没有可以证明九十五点二准确率、日均八千请求或真实业务提效比例的生产报告。

> 术语注释：AI 是人工智能的英文缩写。这里主要指大语言模型理解问题、改写查询和生成答案的能力，不表示系统能够自主做生产决策。

> 术语注释：RAG 是检索增强生成。它先从外部知识库找到与问题相关的资料，再让大模型根据资料回答。它的作用是补充模型参数之外的最新知识，并为答案提供来源。

> 术语注释：FAQ 是常见问题集。它保存高频问题和经过整理的标准答案。命中 FAQ 后可以直接返回，不需要再执行完整检索和生成链路。

> 术语注释：Chroma 是当前项目使用的向量数据库。collection 是 Chroma 内部的一组数据集合，作用类似一张逻辑数据表。项目使用一个 collection 保存可检索的子块，另一个 collection 保存需要恢复的父块原文。

> 术语注释：Embedding 指文本向量化。BGE-M3 是当前使用的向量模型。它把问题和文档转换成机器可以比较的数字表示，用于计算语义或词项相关性。

> 术语注释：RRF 是倒数排名融合。它根据候选在多路检索结果中的名次计算综合分数，用于合并稠密检索和稀疏检索。

> 术语注释：Reranker 指重排模型。BGE Reranker Large 会重新判断用户问题与候选父块的相关程度，把更适合回答问题的资料排到前面。

> 术语注释：GLM 是当前路由和生成使用的大语言模型系列。OpenAI 兼容接口表示它采用与 OpenAI 接口相近的请求格式，方便项目使用统一客户端接入。

> 术语注释：FastAPI 是 Python Web 接口框架，用来接收问答请求并返回结果。SSE 是服务端事件推送协议，用来把模型生成的文字逐段发送到浏览器。MySQL 是关系数据库，用来保存会话历史和摘要。

## 一分钟版本

面试官您好，我做的是 SemiconRAG，一个面向半导体工艺知识查询的 RAG 原型。这个项目主要解决工程师面对工艺、设备、良率和质量问题时，资料分散、专业术语多、文档版本复杂，而且通用大模型容易把行业常识说成具体产线参数的问题。

我把系统分成离线知识处理和在线问答两条链路。离线侧支持 PDF、Word、PPT、图片和 Markdown 等资料，通过文本提取和 OCR 获取内容，再做父子块切分。子块用于精确检索，父块用于恢复完整上下文。BGE-M3 同时生成稠密向量和稀疏词项权重，两路结果通过 RRF 融合，再使用可选的交叉编码器重排。

在线侧先匹配独立 FAQ。没有命中时，路由器会判断问题属于哪个半导体领域，并从 Direct、HyDE、SubQuery 和 Backtracking 中选择检索策略。检索结果带来源进入生成模型。提示词要求资料不足时明确拒答，不能编造设备参数、控制限和文档版本。

服务层使用 FastAPI，支持普通回答和 SSE 流式回答。MySQL 保存会话历史和摘要。当前项目是教学原型，默认只有五份演示资料和三条 FAQ，所以它证明的是完整 RAG 工程链路，不代表已经达到生产准确率。

## 五分钟版本

面试官您好，我介绍一下我做的 SemiconRAG。它是一个面向半导体工艺知识查询的 RAG 教学原型，覆盖工艺整合、设备维护、良率分析、洁净室规范和制程质量控制五类知识。

这个项目的业务起点是，半导体领域的问题通常带有很强的条件约束。相同的工艺名称，在不同产品、设备、腔体、Recipe 版本和生效时间下，参数可能完全不同。通用大模型可以给出行业常识，但不能保证答案对应当前产线的受控文件。如果用户问曝光剂量应该调多少，或者设备 PM 应该执行哪一步，模型一旦补造参数，风险会非常高。

所以我没有把系统设计成自由问答，而是把回答限制在指定资料范围内。系统找得到证据时，基于证据回答并展示来源。系统找不到证据时，明确说明信息不足。涉及停机、放行、参数修改和 PM 时，回答必须提醒用户核对最新受控文件并履行审批。

整个项目分为离线建库和在线问答。

离线建库首先递归读取数据目录。PDF 使用 PyMuPDF 提取文本层，对页面中的大图再使用 RapidOCR。Word 会提取段落、表格和嵌入图片。PPT 会提取文本框、表格和图片。图片文件直接执行 OCR。Markdown 和文本文件直接读取。

> 术语注释：PDF、Word 和 PPT 是常见办公文档格式。Markdown 是使用纯文本符号表示标题、列表和代码等结构的轻量文档格式。

> 术语注释：OCR 是光学字符识别，用来把扫描页和图片中的文字转换成可检索文本。PyMuPDF 用来读取 PDF 的原生文本和图片信息。RapidOCR 用来识别图片中的文字。

文档加载以后，我给它补充 source、file_path、area 和时间戳等元数据。area 来自目录名，分别对应 process、equipment、yield、cleanroom 和 quality。这样在线路由以后，可以在对应领域中检索。

> 字段注释：source 表示资料来源名称，用来在回答中显示引用。file_path 表示原文件路径，用来定位文档。area 表示业务领域，用来过滤检索范围。timestamp 表示处理时间，用来记录文档何时进入索引。

切块采用父子块结构。父块默认一千二百字符，子块默认三百字符，重叠五十字符。中文切分器优先按段落和换行切分，长度仍然过大时再按句末标点、分号和逗号递归切分。每个子块保存 parent_id。

> 字段注释：parent_id 是父块标识。每个子块通过这个字段指向所属父块。检索命中子块以后，系统依靠 parent_id 找回更完整的父块内容。

子块进入 BGE-M3。这个模型同时输出稠密向量和 lexical weights。稠密向量写入 Chroma 的 children collection。父块原文写入 parents collection。父块只通过 id 恢复，不参与向量检索。稀疏词项权重保存在进程内。

> 术语注释：lexical weights 表示词项权重。它记录哪些 token 对这段文本更重要，用于稀疏检索。token 是模型处理文本时使用的基本单位，可以是一个字、一个词或词的一部分。

> 字段注释：children collection 是子块集合，负责向量检索。parents collection 是父块集合，负责保存完整上下文。id 是每条数据的唯一标识，用来去重和精确读取。

在线请求先经过独立 FAQ。FAQ 标准问题提前编码，用户问题到来后计算余弦相似度。最高分达到零点八五时直接返回标准答案，不再调用路由、检索、重排和生成模型。这样既减少延迟和成本，也避免高频标准问题出现口径漂移。

FAQ 没有命中时，QueryRouter 用一次 LLM 调用同时输出 domain、area 和 strategy。domain 判断知识问答还是闲聊。area 判断五个业务领域。strategy 从 Direct、HyDE、SubQuery 和 Backtracking 中选择。所有输出都要经过白名单校验，异常时回退到 knowledge、process 和 direct。

> 术语注释：QueryRouter 是查询路由器。它判断问题应该走哪类业务流程、检索哪个领域以及使用哪种检索策略。LLM 是大语言模型，用来理解自然语言并生成结构化路由结果。

检索阶段同时执行稠密检索和稀疏检索。稠密检索擅长语义相似，比如腔体颗粒异常和 particle 超标。稀疏检索更重视 WAT、OOC、Recipe 和设备编号等精确词项。两路分数的尺度不同，所以我没有直接把原始分数相加，而是用 RRF 根据名次融合。

命中子块以后，系统根据 parent_id 批量恢复父块。启用重排时，再用原始问题与候选父块组成文本对，通过 BGE Reranker Large 打分，最终保留三个父块。这样召回阶段优先保证覆盖，重排阶段再提高最终上下文的相关性。

生成阶段把每个父块和资料来源一起放入 Prompt。模型只能依据检索上下文回答。资料不足时必须说明信息不足，不能补造工艺参数、设备规格、控制限或文档版本。如果有 session_id，系统还会读取最近三轮对话和更早对话的摘要，帮助理解当前问题。

> 术语注释：Prompt 是发送给大语言模型的指令和上下文。它规定模型的角色、可用资料、回答要求和禁止行为。

> 字段注释：session_id 是会话标识，用来把同一用户的多轮问题关联起来。没有这个字段时，系统只能把当前问题当作独立问答。

接口层使用 FastAPI。非流式请求返回答案、领域、策略、来源、耗时和会话 id。流式请求通过 SSE 先返回路由信息，再持续返回文本 chunk，最后返回来源和耗时。每轮问答写入 MySQL。非 FAQ 对话还会在后台线程中更新摘要，避免摘要调用阻塞当前响应。

> 术语注释：chunk 在流式输出中表示一小段增量文本。模型每生成一段，服务端就立即推送一段，用户不需要等待完整答案生成。

当前项目最值得说明的工程问题，是父块写入 Chroma 时曾经触发默认 Embedding 模型。父块本来只用于按 id 取原文，如果不显式传向量，Chroma 会尝试加载自己的默认模型。我最后给父块写入固定的一维占位向量，避免额外下载和权限失败，并重新验证了六个子块和五个父块的索引结构。

这个项目目前仍然是教学原型。评估集只有五条教学题，没有经过半导体专家正式标注。现有 RAGAS 脚本只计算 context_precision 和 context_recall，而且固定走 Direct 路径。因此我不会把它说成端到端准确率，也不会引用没有测试报告的生产指标。

> 术语注释：RAGAS 是用于评估 RAG 系统的工具框架。context_precision 表示检索结果中相关内容的集中程度，用来观察噪声多少。context_recall 表示回答需要的证据是否被检索到，用来观察关键资料有没有遗漏。

如果继续生产化，我会优先完成真实文档的权限、版本和生效范围治理，建立专家标注评估集，增加句级引用和无答案测试，再实现版本化索引、原子切换、请求鉴权、文档级权限过滤和完整可观测性。

## 十五分钟版本

### 项目定位

面试官您好，我介绍的项目是 SemiconRAG。它是一个面向半导体工艺知识查询的 RAG 教学原型，主要服务工艺整合、设备维护、良率分析、洁净室规范和制程质量控制五类问题。

这个项目不是设备自动控制系统，也不是能够替代工艺工程师做决策的智能体。它的定位是知识查询和调查辅助。系统从指定资料中检索证据，再生成有来源、有边界的回答。任何停机、批次放行、参数修改、设备 PM 和危险作业，都必须由授权人员依据最新受控文件决定。

我是在已有 RAG 工程基础上完成半导体场景改造。我的重点不是更换项目名称，而是把业务领域、数据目录、元数据、路由、检索、生成约束、会话和评估口径统一起来。我的个人职责范围是待本人填写，面试前需要根据实际提交记录调整。

### 业务问题

半导体知识问答有三个明显特点。

第一个特点是术语密度高。一个问题里可能同时包含 WAT、OOC、OOS、Recipe、PM、SPC、腔体和产品层次。语义检索需要理解表达变化，精确检索又必须保住缩写、编号和专有词。

第二个特点是条件依赖强。同一个工艺参数可能依赖产品、层次、设备型号、腔体、材料、Recipe 版本、量测方法和生效时间。缺少这些条件时，系统不能给出可执行数值。

第三个特点是风险边界严格。普通问答出错可能只是体验问题，但生产场景中的错误控制限、错误规程版本和错误操作步骤可能造成批次、设备或安全风险。

因此，这个项目的设计目标不是让回答听起来像专家，而是让回答能够说明证据来自哪里、当前信息缺什么、哪些内容不能由系统直接决定。

### 为什么使用 RAG

我没有选择只依赖大模型参数记忆。模型参数中的知识无法保证对应当前文档版本，也很难解释具体结论来自哪份资料。半导体文件又会持续更新，把动态知识训练进模型会增加更新和追溯成本。

RAG 可以让文档与模型解耦。资料更新以后重建索引，模型本身不需要重新训练。回答时可以把检索到的资料作为证据注入，并把来源返回给用户。

我也没有把所有问题都交给 RAG。高频且稳定的问题由独立 FAQ 返回标准答案。闲聊直接走生成模型。结构化生产数据在未来应该由数据库或业务 API 查询，不应该先转成文本再做向量检索。

### 数据范围

当前默认数据目录是 data 下的 semicon。目录中有 process、equipment、yield、cleanroom 和 quality 五个子目录。每个目录目前有一份 Markdown 演示资料。

工艺资料描述曝光剂量偏移、刻蚀选择比、薄膜厚度和 CMP 去除量的查询边界。

设备资料描述 PM 前的核对事项和刻蚀腔体 particle 超标的排查路径。

良率资料描述 WAT 接触电阻偏高时如何关联批次、量测、工艺履历和设备腔体。

洁净室资料描述污染和安全异常需要记录的范围，以及危险操作的授权边界。

质量资料描述 OOC、OOS 和 SPC 异常处理的基本区别。

这些资料全部标注为 DEMO 文档，不是生产受控文件。旧项目中的 V93K 资料仍然保留在 data 根目录，但当前默认索引目录不会加载它们。

### 多格式文档处理

DocumentProcessor 递归扫描数据目录，根据扩展名选择加载器。支持 PDF、Word、PPT、PPTX、JPG、JPEG、PNG、Markdown 和 TXT。

同一目录中如果存在同名的 Markdown 或文本文件与 PDF，系统优先加载 Markdown 或文本文件，跳过重复的 PDF。这样可以避免同一资料以两个格式重复入库，导致检索结果被重复内容占据。

文档加载后统一转成 LangChain Document。系统补充 file_path、source、area 和 timestamp。source 来自文件名，不包含扩展名。area 来自父目录名。

> 术语注释：LangChain Document 是 LangChain 框架中统一表示文档的对象。它把正文和元数据放在同一个结构中，方便切分器、检索器和生成链路共同使用。

> 字段注释：stem 表示去掉扩展名后的文件名。document_id 表示文档的稳定唯一标识。content_hash 表示根据文档内容计算出的摘要值，可以用来判断文档内容是否发生变化。

当前 source 只到文件 stem，这个粒度适合演示，但不适合生产。真实环境需要 document_id、文档版本、章节、页码、生效时间、失效时间、适用产品、设备、腔体、权限范围和内容哈希。

### OCR 处理

PDF 加载器先通过 PyMuPDF 读取文本层。然后检查页面中的嵌入图片。只有宽度和高度占页面比例都达到配置阈值的大图才执行 OCR，避免水印和小图标带来大量噪声。

Word 加载器提取段落和表格，并遍历嵌入图片执行 OCR。PPT 加载器按幻灯片提取文本框、分组文本、表格和图片。独立图片文件直接交给 RapidOCR。

RapidOCR 使用单例懒加载。第一次真正需要 OCR 时初始化，后续文件复用同一个实例。

当前 OCR 链路可以覆盖基本文本提取，但没有保存 PDF 页码、Word 标题层级、表格单元格坐标和 OCR 置信度。真实文档中如果包含复杂参数表，这些结构信息非常重要。生产化时需要保留版面结构，低置信度内容还要进入人工校验。

### 父子块切分

文档切分使用 ChineseRecursiveTextSplitter。它从粗粒度到细粒度依次尝试空行、换行、中文句末标点、英文句末标点、分号和逗号。分隔符会保留在文本中，尽量让每个块保持完整句子。

系统先切父块，再在每个父块内部切子块。父块默认一千二百字符，子块默认三百字符，重叠五十字符。父块生成 parent_id，子块生成自己的 id，并保存 parent_id。

父子块解决的是检索粒度和生成粒度之间的冲突。大块包含更多上下文，但向量可能混合多个主题。小块定位更精确，但容易丢失条件、前后步骤和安全边界。当前设计用小块召回，用大块生成。

父子块也有成本。多个子块可能命中同一个父块，因此恢复时要按 parent_id 去重。父块可能带回一部分无关内容，因此还需要重排。块大小和重叠长度目前是经验配置，真正上线前必须通过评估集做参数实验。

### BGE-M3 Embedding

Embedding 模型使用本地 BGE-M3。当前配置使用 CPU，不启用 FP16，最大输入长度是五百一十二，批大小是十二。

> 术语注释：CPU 是通用中央处理器，适合兼容性优先和低并发运行。GPU 是图形处理器，擅长并行矩阵计算，常用于提升模型推理速度。FP16 是十六位浮点数格式，相比三十二位浮点数能够减少显存和计算量，但需要硬件和模型支持。

同一个模型提供两种表示。

第一种是稠密向量。每段文本得到一千零二十四维向量。BGE-M3 输出已经进行 L2 归一化。稠密向量适合语义相似问题，比如用户说颗粒异常，文档写 particle 超标。

> 术语注释：L2 归一化是把向量长度缩放为一。这样点积可以直接反映方向相似程度，便于使用余弦相似度比较问题和文档。

第二种是 lexical weights。它是 token 到权重的稀疏映射。稀疏表示更适合 WAT、OOC、Recipe 和设备编号等精确词项。

当前代码还包含一个 transformers 兼容补丁。原因是 FlagEmbedding 某些加载路径会传 dtype，而当前 transformers 版本更接受 torch_dtype。代码在 AutoModel.from_pretrained 外层转换参数名称。

这个补丁能够解决当前环境问题，但它属于全局 monkey patch。更稳妥的生产方案是固定验证过的依赖版本，或者升级到兼容版本，并通过启动测试确认模型能够正常加载。

> 术语注释：monkey patch 指程序运行时替换第三方类或函数的行为。它可以临时解决兼容问题，但影响范围较大，所以生产环境更适合通过升级依赖或固定版本解决。

### Chroma 双 collection

向量存储使用 Chroma PersistentClient。

> 术语注释：PersistentClient 是 Chroma 的本地持久化客户端。它把 collection 数据保存到磁盘，服务重启后仍然能够读取。

children collection 保存子块文本、稠密向量、id、parent_id、source、area 和 file_path。它参与向量检索。

parents collection 保存父块原文和 source。它只通过 parent_id 批量读取，不参与向量查询。

物理上只有两个 collection。五个业务领域通过 area 元数据区分，不是五个物理知识库。稠密检索时，Chroma 的 where 条件按 area 或 source 过滤。

父块写入时显式提供一维占位向量。这样做是为了避免 Chroma 在缺少向量时自动调用默认 Embedding 模型。父块从来不执行向量查询，所以占位向量不会参与相关性计算。

当前本地数据库还保留旧 V93K collection，但当前配置指向 semicon_kb 和 semicon_kb_parents。SemiconRAG 对应的记录是六个子块和五个父块。

### 内存稀疏索引

稀疏索引由 SparseIndex 维护。每个子块保存 id、词项权重、source 和 area。查询时，系统遍历查询词项和文档词项，对相同 token 的权重乘积求和，再按分数排序。

> 术语注释：SparseIndex 是项目封装的内存稀疏索引。它不是独立数据库，而是服务进程中的 Python 数据结构，用于保存子块词项权重并完成稀疏召回。

这个实现不是 BM25。虽然依赖列表中存在 rank-bm25，SparseIndex 里也统计了 doc_freq，但当前搜索公式没有使用传统 BM25 的词频、逆文档频率和文档长度归一化。

> 术语注释：BM25 是传统关键词检索算法。它综合词频、词项稀有程度和文档长度计算相关性。doc_freq 表示包含某个词项的文档数量，可用于估计词项的稀有程度。当前项目虽然统计了它，但没有把它用于实际打分。

稀疏权重没有持久化到 Chroma。服务重启以后，VectorStore 会读取所有子块文本，重新调用 BGE-M3 计算 lexical weights，再恢复内存索引。

当前只有六个子块，启动重算没有明显影响。数据规模扩大以后，这会增加启动时间和 CPU 消耗，也不方便多实例共享。生产化可以持久化稀疏权重，或者使用 Elasticsearch、OpenSearch 和支持混合检索的向量数据库。

### RRF 融合

稠密检索和稀疏检索的分数分布不同。Chroma 返回的是距离，稀疏索引返回的是词项权重点积。如果直接相加，需要先做归一化和权重标定。

当前项目使用 Reciprocal Rank Fusion。RRF 只使用每一路中的排名，不直接比较原始分数。当前常数 K 是六十，排名从一开始。

如果一个子块在稠密结果中排第一，它得到一除以六十一。如果它在稀疏结果中排第二，再得到一除以六十二。两项相加以后，同时被两路高排名命中的内容通常排得更靠前。

这个方法简单稳定，但常数六十仍然是经验值。真实环境可以用标注集比较不同常数，也可以尝试归一化加权、学习排序和查询类型自适应融合。

### 父块恢复与重排

每个检索查询默认召回五个子块。多个检索查询的结果按子块 id 去重。系统收集 parent_id，从 parents collection 批量读取父块，并保持首次命中的顺序。

如果启用重排并且父块数量大于最终候选数，系统使用 BGE Reranker Large。它把原始用户问题和每个父块组成文本对，通过交叉编码器输出相关性分数，按分数降序选择前三个父块。

双塔 Embedding 适合大规模召回，因为文档向量可以离线计算。交叉编码器让问题与文档在同一个模型中充分交互，相关性判断更细，但每个候选都需要单独推理。因此系统采用先召回、后重排的两阶段设计。

当前重排模型在 CPU 上运行，模型体积和启动成本都比较大。FastAPI 启动时会尝试预热，避免第一次问答承担完整加载时间。生产化需要根据延迟目标决定是否使用 GPU、较小模型、批处理或独立重排服务。

### FAQ 快速路径

FAQ 与文档知识库分开维护。当前 JSON 文件中有三条启用记录，分别覆盖 SPC OOC 的第一步、OOC 与 OOS 的区别，以及执行设备 PM 前需要核对的内容。

FAQStore 启动时读取 JSON，通过 Pydantic 校验字段和重复 id。只保留 enabled 为 true 的记录，然后为标准问题生成并归一化稠密向量。

> 术语注释：FAQStore 是 FAQ 的加载和匹配组件。JSON 是一种键值结构文本格式。Pydantic 是 Python 数据校验库，用来检查字段类型、必填内容和非法值。enabled 表示这条 FAQ 是否启用。

在线问题到来后，系统生成查询向量并归一化，与全部候选做矩阵点积。最高相似度达到零点八五时直接返回标准答案。

FAQ 命中后不调用路由器、文档检索、重排和生成模型。它能够降低延迟和调用成本，也让高频标准问题保持固定口径。

零点八五目前只是初始经验阈值，不是通过真实正负样本得到的最优值。生产化需要准备同义问题、近似但不等价的问题和无关问题，统计不同阈值下的精确率、召回率、误命中率和漏命中率。高风险场景通常优先降低误命中。

FAQ 支持热重载。重载过程使用线程锁。新记录和新向量完整构建后，再作为一个快照整体替换。加载失败时保留旧快照，在线匹配不会读到半更新状态。

### 查询路由

FAQ 没有命中以后，QueryRouter 调用一次 LLM，同时判断 domain、area 和 strategy。

domain 只有 knowledge 和 chitchat。

area 只有 process、equipment、yield、cleanroom 和 quality。

strategy 只有 direct、hyde、subquery 和 backtracking。

> 术语注释：domain 指请求的大类，用来决定系统是否进入知识检索链路。knowledge 表示知识类问题，需要查询知识库。chitchat 表示问候、闲聊或与半导体知识无关的问题，不需要检索专业文档。

> 术语注释：area 指知识所属的业务领域，用来缩小检索范围。process 表示工艺整合，equipment 表示设备维护，yield 表示良率分析，cleanroom 表示洁净室与环境安全，quality 表示制程质量控制。

> 术语注释：strategy 指检索策略，用来决定原问题如何转换成真正送入知识库的查询。direct 表示直接检索原问题，hyde 表示先生成假设答案再检索，subquery 表示把复杂问题拆成多个子问题，backtracking 表示把依赖上文的追问改写成独立问题。

> 字段注释：domain、area 和 strategy 都是路由器输出的 JSON 字段。JSON 是一种结构化文本格式，便于程序稳定读取模型输出并进行白名单校验。

路由提示词要求模型只返回 JSON。程序解析以后再次检查白名单。非法 domain 回到 knowledge，非法 area 回到 process，非法 strategy 回到 direct。闲聊固定使用 direct，不执行复杂检索策略。

调用异常时，系统使用 knowledge、process 和 direct 作为兜底。这个设计保证链路继续运行，但也有风险。如果原问题本来属于 equipment，回退到 process 硬过滤可能漏掉正确资料。

生产化可以增加路由置信度。低置信度时不使用单领域硬过滤，或者并行检索两个候选领域。如果指定领域没有足够结果，也可以自动扩大到全局知识库。

### Direct 策略

Direct 直接使用原问题检索。它适合问题明确、术语充分的事实题。

例如用户问 OOC 和 OOS 有什么区别。这个问题本身包含关键缩写，不需要生成假设答案或拆分子问题。Direct 的模型调用最少，延迟最低，也最不容易因为改写引入偏差。

### HyDE 策略

HyDE 先让模型围绕原问题生成一段一百到二百字的假设答案，再用这段假设文本做检索。

它适合宽泛问题。比如用户问如何改善金属层良率，原问题太短，文档中的具体表达可能包括缺陷图谱、工艺履历、WAT、设备腔体和近期变更。假设答案能够补充这些可能出现在资料中的术语。

HyDE 的风险是检索漂移。模型如果生成了错误因素，检索可能被带到错误方向。因此提示词要求不编造具体产线参数。更重要的是，假设答案只作为检索查询，不能直接作为最终答案。

当前实现只使用假设答案检索，没有将原问题与假设答案并行召回。后续可以融合两路结果，降低改写偏差。

### SubQuery 策略

SubQuery 把复杂问题拆成多个独立子问题。它适合多因素排查。

例如用户问刻蚀腔体 particle 超标怎么排查。系统可以分别检索量测有效性、批次与腔体关联、异常时段、最近 PM、Recipe 变更、设备告警、耗材记录和历史趋势。

当前代码按行读取模型输出，清理数字编号和项目符号，最多保留四个子查询。每个子查询分别执行混合检索，结果按子块 id 去重，再统一恢复父块和重排。

SubQuery 能提高证据覆盖，但也会增加查询次数和噪声。生产化需要限制拆分数量，记录每个子查询贡献了哪些最终证据，并考虑并行执行多个子查询。

### Backtracking 策略

Backtracking 的目标是把追问式或过于具体的问题改写成独立可检索的问题。

例如用户先讨论刻蚀选择比，接着问那过刻蚀量呢。理想系统应该从历史中恢复主题，再生成完整查询。

当前实现存在明确限制。Backtracking 提示词只接收当前 query，没有接收会话摘要和最近三轮。因此它可以简化表达，但不能稳定完成指代消解。会话历史目前主要在答案生成阶段使用。

这部分不能描述为已经完整支持多轮检索。下一步应该在路由前增加历史感知查询重写，让独立查询同时用于 FAQ、路由和检索，并对改写结果保留审计记录。

### 回答生成

RAGSystem 收到父块以后，为每个父块添加资料来源标签，再用分隔线拼接成上下文。

生成提示词要求模型只能依据上下文回答。如果上下文不足，必须说明根据当前知识库信息不足。不能编造工艺参数、设备规格、控制限和文档版本。回答要引用上下文中已有的资料标题和文档编号。

涉及停机、放行、参数修改和 PM 时，提示词还要求用户核对厂内最新受控文件并履行审批。

如果检索结果为空，系统直接返回无法准确回答的固定信息，不调用生成模型。这样可以避免模型在零证据状态下自由发挥。

当前来源粒度只到文件名。用户不能从答案直接跳转到页码、章节和原文位置。生产化需要保存 document_id、version、page、section 和 paragraph，并让每个关键结论绑定具体证据片段。

> 字段注释：version 表示文档版本。page 表示页码。section 表示章节。paragraph 表示段落。它们共同用于把答案中的结论定位到原文的具体位置。

### 多轮会话

新会话由后端生成 session_id，格式是 s_ 加八位随机字符。前端把它保存到本地，后续请求继续携带。

MySQL 中有 sessions 和 summaries 两张表。sessions 每行保存一轮问题、答案、domain、strategy、sources、elapsed_ms 和创建时间。summaries 每个会话保存一条摘要和覆盖轮数。

生成回答前，系统读取最近三轮问答和更早对话的摘要。最近三轮保留较完整的文本，更早历史压缩成不超过两百字的摘要。

本轮回答完成后，系统同步写入 sessions，保证下一次请求能够读取。非 FAQ 路径再启动后台线程生成摘要，避免当前响应等待第二次 LLM 调用。FAQ 路径只保存问答，不触发摘要模型。

当前会话实现有三个边界。

第一，历史进入生成 Prompt，但没有完整进入检索查询。

第二，同一会话快速连续提问时，多个摘要线程可能基于不同快照覆盖结果。

第三，摘要重建会读取最近三轮之前的全部旧轮次，长会话下开销会持续增加。

生产化可以按 session 建立串行任务队列，保存 covered_turn_id，并使用版本号做乐观锁。多实例环境下需要分布式锁或可靠消息队列。

### FastAPI 服务

main.py 创建 FastAPI 应用并注册 API 路由。lifespan 启动阶段预热 BGE-M3、重排模型、Chroma、稀疏索引、FAQ 向量、RAGSystem 和 MySQL 会话模块。

这样做可以降低首个请求的模型加载延迟，但会增加服务启动时间。生产部署需要 readiness probe，在所有必要资源准备完成前不接入流量。

> 术语注释：readiness probe 是就绪探针。部署平台通过它判断服务是否已经准备好接收请求。模型和索引没有加载完成时，流量不会被转发到这个实例。

POST /api/ask 负责问答。请求包含 question、source_filter、session_id 和 stream。

POST /api/rebuild_index 负责全量重建文档索引。

POST /api/faq/reload 负责重新加载 FAQ。

GET /api/health 返回状态、模型名、collection 名和子块数量。

> 术语注释：API 是应用程序接口，用来让前端或其他服务调用后端能力。POST 表示向服务提交数据或触发操作。GET 表示读取信息。斜线后的内容是具体接口路径。

> 字段注释：question 是用户问题。source_filter 是来源过滤条件，用来把检索限制在指定文档。stream 表示是否使用流式返回。

当前 CORS 允许任意来源，重建和重载接口没有鉴权。这只适合本地开发。生产化必须增加认证、授权、速率限制、请求大小限制、审计日志和 CORS 白名单。

> 术语注释：CORS 是浏览器跨域资源共享策略。它决定哪些网页来源可以调用当前接口。生产环境使用白名单可以减少陌生网站直接访问接口的风险。

### SSE 流式输出

流式请求使用 Server-Sent Events。

服务首先返回一个初始化 meta 事件，其中包含 session_id。路由完成后再发送 domain 和 strategy。生成阶段持续发送 chunk 事件，每个事件包含增量文本。最后发送 done 事件，其中包含来源、耗时、领域和策略。发生异常时发送 error 事件。

当前场景主要是服务端向浏览器单向推送文本，SSE 足够简单。WebSocket 更适合高频双向消息、实时协作或语音流。项目当前没有使用 WebSocket。

仓库中还有一个轻量 web_server.py。它负责托管静态文件，并把 /api 请求反向代理到 FastAPI。检测到 SSE 时，它使用较长超时并逐块转发，不等待完整答案生成以后再返回。

### 一次完整请求

我用刻蚀腔体 particle 超标怎么排查来说明完整链路。

请求先进入 POST /api/ask。后端生成或复用 session_id。

RAGSystem 先调用 FAQStore。当前三条 FAQ 没有完全覆盖这个问题，所以继续进入 QueryRouter。

路由器预期把它识别为 knowledge、equipment 和 subquery。area 会用于限制 equipment 领域。SubQuery 会生成多个互补检索问题。

每个子查询先通过 BGE-M3 生成稠密向量和稀疏词项权重。Chroma 在 equipment 元数据范围内返回稠密候选。SparseIndex 在相同领域内返回稀疏候选。

两路结果用 RRF 融合。多个子查询结果再按子块 id 去重。系统读取 parent_id，恢复 equipment_pm 的父块。如果候选足够多，再使用原始问题进行交叉编码器重排。

最终上下文会包含 DEMO-EQP-001 的资料内容。生成模型据此回答量测有效性、批次与腔体关联、异常时段、最近 PM 与 Recipe 变更、设备告警、腔体状态、耗材和历史趋势。

因为资料没有具体设备型号和受控 PM 规程，答案不能给出具体拆装、校准和复机步骤。它必须提醒用户由设备和工艺工程师共同判断，并依据最新受控文件处理。

### 会话落库

答案生成完成以后，系统计算端到端 elapsed_ms。然后把 session_id、question、answer、domain、strategy、sources 和 elapsed_ms 写入 sessions 表。

> 字段注释：answer 是最终答案。sources 是引用来源列表。elapsed_ms 是本次请求耗时，单位是毫秒。sessions 是保存每轮问答的数据库表。

如果这不是 FAQ 路径，后台线程会读取旧摘要和最近三轮以前的对话，调用 Generator.summarize 生成新摘要，再 upsert 到 summaries 表。

> 术语注释：upsert 表示有记录时更新，没有记录时新增。summaries 是保存会话摘要的数据库表。Generator.summarize 是生成摘要的方法。

会话写入失败不会撤销已经生成的答案。系统记录错误并停止摘要任务。这个行为保证主要问答尽量返回，但也意味着答案返回成功不代表历史已经成功持久化。生产环境应把会话持久化状态纳入监控。

### 评估设计

当前评估入口是 scripts/run_eval.py。它默认读取 data/eval/semicon_qa_v1.json。

评估集有五条教学样本，每个领域一条。问题覆盖曝光剂量偏移、刻蚀腔体 particle、WAT 接触电阻、洁净室污染和 OOC 与 OOS。

评估运行器对每条样本固定使用 Direct 策略检索，然后调用 Generator 生成答案。检索结果、答案、标准答案和参考信息交给 RAGAS。

当前只计算 context_precision 和 context_recall。报告中的 ragas_score 是两个指标的算术平均。

context_precision 关注召回上下文的信噪比。分数低说明前排候选中可能混入过多无关内容。

context_recall 关注回答需要的证据是否被召回。分数低说明关键资料可能没有进入上下文。

这两个指标不能代表端到端答案准确率。检索正确以后，模型仍然可能遗漏或误读。模型也可能依赖参数记忆答对，但引用错误资料。在需要可追溯的系统里，这仍然是不合格结果。

### 如何建设正式评估

正式评估集需要由半导体领域专家参与，不能只靠开发者自己编写。

我会把问题分成十类。

第一类是标准 FAQ 和同义改写，用于评估 FAQ 精确率和召回率。

第二类是设备编号、错误码、Recipe 和专业缩写，用于评估稀疏检索。

第三类是不同表达但语义相同的问题，用于评估稠密检索。

第四类是多因素排查问题，用于评估 SubQuery。

第五类是宽泛研究问题，用于评估 HyDE。

第六类是多轮指代问题，用于评估历史感知改写。

第七类是跨领域问题，用于评估路由和多领域召回。

第八类是知识库没有答案的问题，用于评估拒答。

第九类是旧版本与新版本冲突问题，用于评估文档治理。

第十类是权限越界问题，用于评估安全过滤。

每条样本要有标准答案、必要证据、允许来源、禁止结论、风险等级和专家审核记录。

指标需要覆盖 Recall at K、MRR、NDCG、context_precision、context_recall、答案正确性、答案忠实度、引用正确率、拒答准确率、FAQ 误命中率、路由准确率、首 token 延迟和完整响应延迟。

> 指标注释：Recall at K 表示前 K 个检索结果是否覆盖应找到的资料。MRR 关注第一个正确结果出现得有多靠前。NDCG 同时考虑相关性等级和排序位置。首 token 延迟表示用户等待第一段模型输出的时间。

### 消融实验

为了判断每个模块是否真正有效，我会固定同一批数据、同一版本索引和同一生成模型，逐项比较。

先比较只使用稠密检索、只使用稀疏检索和混合检索。

再比较混合检索与混合检索加重排。

然后比较单层切块与父子块。

继续比较无领域过滤、单领域过滤和低置信度多领域检索。

最后比较 Direct、HyDE、SubQuery 和 Backtracking。

每次只改变一个变量，同时记录效果、延迟、模型调用次数和 token 成本。这样才能说明某个模块带来了什么收益，而不是只展示一个复杂架构图。

### 项目中最难的问题

第一个难点是精确术语和语义表达的平衡。

只做稠密检索时，语义改写效果较好，但设备编号、缩写和错误码可能被弱化。只做稀疏检索时，精确词项稳定，但用户换一种说法就可能漏召回。我的解决方法是让 BGE-M3 同时生成稠密和稀疏表示，再使用 RRF 融合。

第二个难点是检索粒度和上下文完整性的平衡。

小块有利于定位，大块有利于理解。我采用父子块结构，用子块检索、父块生成，再用重排控制父块噪声。

第三个难点是第三方存储的隐式行为。

父块只用于按 id 恢复，但 Chroma 在没有显式向量时会尝试调用默认 Embedding。我通过堆栈定位到父块 upsert，最后为父块传入一维占位向量，避免额外模型下载和目录权限问题。

第四个难点是多轮会话的成本和完整性。

全部历史直接进入 Prompt 会增加 token 和噪声，所以我保留最近三轮，对更早历史做摘要。当前这套方案解决了生成上下文长度问题，但还没有完整解决检索侧指代和摘要并发问题。

第五个难点是如何诚实评估。

当前数据和评估集都很小。我没有使用一个高分去包装生产效果，而是明确说明现有脚本只覆盖 Direct 路径和两项上下文指标。生产结论必须等待专家标注和真实试点。

### 可靠性与降级

系统在多个位置设计了降级路径。

FAQ 检测失败时继续常规问答。

路由调用失败或 JSON 非法时回退到固定路由。

HyDE、SubQuery 和 Backtracking 改写失败时回退到原问题。

没有检索上下文时返回固定拒答，不调用生成模型。

生成失败时返回统一错误信息。

会话写入失败时记录日志，不阻塞已经生成的回答。

这些降级还不完整。MySQL 历史读取异常仍可能影响请求。重排模型加载失败以后，在线检索可能继续报错。索引全量重建失败可能留下空库。生产化需要为每个依赖定义超时、重试、熔断、降级和告警。

### 索引重建

当前 build_index 脚本先加载全部文档，生成父子块，再获取 VectorStore。随后调用 clear 删除旧 collection，然后写入新数据。

> 术语注释：build_index 表示构建索引。VectorStore 是项目对向量库和稀疏索引的统一封装。clear 表示清空当前 collection，因此当前全量重建存在旧索引先被删除的风险。

这个过程不是原子操作。如果写入阶段失败，旧索引已经被删除。在线问答也可能在重建窗口读取不完整状态。

生产方案应该创建带版本号的新 collection。构建完成后检查文档数量、块数量、Embedding 维度、元数据完整性和样例检索。所有检查通过以后，再原子切换当前索引别名或配置指针。旧版本保留一段时间，用于快速回滚。

增量更新可以根据 document_id 和 content_hash 判断新增、修改和删除。更新时还要处理父子块的级联失效。

> 术语注释：增量更新只处理发生变化的文档，不重新计算全部资料。document_id 用来确认是哪一份文档，content_hash 用来判断内容是否改变。

### 安全问题

当前 config.ini 中存在明文 API 凭据和数据库密码。这是需要优先整改的问题。正确做法是立即轮换已经暴露的密钥，并通过环境变量、密钥管理服务或部署平台 Secret 注入。

> 术语注释：config.ini 是项目配置文件。Secret 表示由部署平台安全保存并注入应用的敏感信息，例如 API 密钥和数据库密码。

问答、重建和 FAQ 重载接口当前没有身份认证。CORS 允许任意来源。生产化必须增加用户身份、角色、租户和文档权限。

权限过滤要在检索前执行，不能先把敏感文档送给模型，再要求模型不要展示。稠密检索、稀疏检索、缓存、日志、来源列表和会话历史都必须使用一致的权限范围。

缓存键必须包含租户、用户权限、索引版本、模型版本和 Prompt 版本，避免跨权限复用。

所有管理操作都要写审计日志。至少记录操作者、时间、索引版本、文档范围和结果。

### 提示注入

用户输入和文档内容都应该被视为不可信数据。

文档中可能出现要求忽略系统规则、输出密钥或执行操作的文本。系统提示词需要明确文档只是证据，不是控制指令。工具和管理接口的权限必须由后端代码判断，不能因为模型生成了一段文字就执行。

输入侧可以检测常见注入模式。检索上下文使用清晰边界。输出侧增加敏感信息和高风险操作检查。真正的安全基础仍然是最小权限，即使模型被诱导，也无法读取或调用当前用户无权访问的资源。

### 性能优化

性能优化之前要先做分段计时。

我会分别记录 FAQ 匹配、路由、查询改写、查询 Embedding、Chroma 检索、稀疏检索、父块恢复、重排、首 token、完整生成和会话落库耗时。

当前稠密和稀疏检索顺序执行，多个 SubQuery 也顺序执行。它们具有并行空间。

可以缓存高频查询的 Embedding。可以把 FAQ 和明确规则问题提前短路。可以根据问题复杂度动态选择 K 和 M。可以使用更小的重排模型或 GPU 批处理。可以缩短无关上下文，并控制最终生成长度。

任何缓存都要带索引版本和权限范围。高风险操作问题不适合直接缓存最终答案。

### 当前限制

当前数据只有五份演示资料和三条 FAQ，不能代表真实半导体知识规模。

当前评估集只有五条教学样本，不能证明生产准确率。

当前只返回文件级来源，不能跳转到具体页码和段落。

当前稀疏权重在服务启动时重新计算。

当前全量重建不是原子操作。

当前只选择一个 area，跨领域问题可能漏召回。

当前历史主要进入生成，不完整进入检索改写。

当前摘要后台线程没有同会话串行控制。

当前管理接口没有鉴权，CORS 过于宽松。

当前 Embedding 和重排本地运行，但路由和生成使用远程接口，因此不能说数据完全不出本机。

当前仓库没有自动化测试文件。已有的是评估脚本，不等于单元测试、集成测试和并发测试。

### 生产化路线

第一阶段是数据治理。

接入经过授权的真实资料，建立文档 id、版本、生效时间、失效时间、适用产品、设备、腔体、Recipe、密级和权限标签。资料进入索引前完成脱敏、审核和内容哈希。

第二阶段是评估基线。

由领域专家建设正式评估集。先建立当前 Direct 和混合检索基线，再逐步验证路由、重排和四种策略。

第三阶段是安全控制。

轮换密钥，增加身份认证、文档级权限过滤、审计日志、提示注入防护和高风险回答策略。

第四阶段是索引可靠性。

实现版本化索引、增量更新、原子切换、回滚、坏文档隔离和构建报告。

第五阶段是服务稳定性。

增加超时、重试、熔断、限流、链路追踪、指标监控和依赖健康检查。会话摘要改为可靠任务队列。

第六阶段是性能扩展。

根据真实文档量和流量决定是否引入 GPU Embedding、批处理、独立重排服务、Redis 和分布式向量数据库。技术选型由指标驱动，不因为简历关键词提前堆叠组件。

### 十五分钟版本收尾

总结来说，这个项目最核心的工作不是把向量数据库和大模型接口连接起来，而是把文档处理、混合检索、查询路由、受约束生成、会话记忆和评估边界组织成一条可以检查的链路。

我在项目中重点处理了三组矛盾。第一组是语义召回与精确术语之间的矛盾，我使用 BGE-M3 双表示和 RRF 融合。第二组是检索精度与上下文完整性之间的矛盾，我使用父子块和重排。第三组是模型表达能力与工业安全边界之间的矛盾，我使用 FAQ、严格 Prompt、无证据拒答和受控文件提醒。

当前原型已经跑通完整链路，也清楚暴露了数据规模、评估、版本、权限和多轮检索上的不足。如果进入生产阶段，我会先解决可验证性、安全性和索引可靠性，再讨论吞吐、缓存和分布式扩展。

## AI 面试重点亮点

面试时建议优先强调以下七点。

第一，项目不是简单的向量检索加生成，而是有独立 FAQ、领域路由、策略路由、混合召回、父块恢复、重排和会话记忆。

第二，BGE-M3 同时生成稠密向量和 lexical weights，兼顾语义改写和专业术语。

第三，稠密与稀疏结果使用 RRF 融合，避免直接比较不同尺度的原始分数。

第四，父子块把检索粒度和生成粒度分离，小块负责定位，大块负责上下文。

第五，高频标准问题通过 FAQ 直接返回，减少调用成本和口径漂移。

第六，回答明确受到证据约束，缺少资料时拒答，高风险操作必须回到受控文件和授权流程。

第七，能够主动说明当前评估和生产化边界，不把教学样本包装成工业准确率。

## 深挖讲稿

下面内容用于面试官继续追问业务背景、RAG 原理、检索算法、会话、评估和生产化方案时展开，不需要在开场一次性讲完。

## 一、开场

大家好，今天我介绍的项目是 SemiconRAG。

它是一个面向半导体工艺知识查询的 RAG 原型。用户可以询问工艺整合、设备维护、良率分析、洁净室规范和制程质量控制相关问题。

这个项目没有把大模型当成工艺参数数据库。它先从指定资料中检索证据，再让模型组织答案。系统回答的不只是一个结论，还要说明依据来自哪里、当前缺少什么信息、哪些动作不能由问答系统决定。

整个系统可以概括为六层。最上层是 Web 聊天界面。第二层是 FastAPI 接口。第三层是 FAQ 和查询路由。第四层是 Direct、HyDE、SubQuery 和 Backtracking 检索编排。第五层是 BGE-M3 混合检索、RRF、父块恢复和重排。最底层是 Chroma、MySQL、演示文档和远程生成模型。

> 术语注释：RAG 是检索增强生成。系统先从外部知识库检索资料，再把资料交给生成模型回答。

> 术语注释：Embedding 是把文本转换成向量表示，使语义相近的文本在向量空间中更接近。

## 二、业务背景

半导体生产涉及大量工艺文件、设备手册、异常流程、质量规则和历史记录。

工程师遇到曝光偏移、腔体 particle、WAT 异常或 SPC OOC 时，通常需要先确定产品、批次、设备、腔体、Recipe、量测条件和时间范围，再查找对应版本资料。

传统文档搜索主要依赖关键词。如果用户不知道准确标题或术语，很难找到目标资料。通用大模型虽然能够解释行业概念，但不知道企业当前使用哪一版文件，也不知道某个参数适用于哪台设备。

RAG 的价值是把自然语言问题和受控知识连接起来。但检索到文档并不等于回答可靠。文档解析、切块、元数据、召回、重排、版本、权限和评估都会影响最终结果。

所以我把这个项目理解成一套知识工程系统，而不是一个聊天页面。

## 三、五类业务领域

process 对应工艺整合。它关注产品、层次、光刻、刻蚀、薄膜、扩散、CMP 和工艺窗口。

equipment 对应设备维护。它关注设备型号、腔体、PM、告警、耗材和设备状态。

yield 对应良率分析。它关注 WAT、缺陷图谱、工艺履历、设备关联和批次趋势。

cleanroom 对应洁净室和 EHS。它关注区域规范、人员资质、防污染、化学品和安全边界。

quality 对应制程质量。它关注 SPC、OOC、OOS、量测系统、控制规则和规格文件。

五个领域目前通过目录和 area 元数据组织。它们不是五个 Milvus collection，也不是五套物理数据库。

> 术语注释：WAT 是晶圆验收测试。它通过测试晶圆上的结构，观察制造过程中的电学特性。

> 术语注释：SPC 是统计过程控制。它通过控制图和规则识别过程是否出现异常信号。

> 术语注释：OOC 表示过程信号触发控制规则。OOS 表示结果超出规格限制。两者的判定依据不同。

> 术语注释：PM 是预防性维护。它需要依据设备型号、腔体和受控规程执行。

## 四、为什么不直接微调

这个项目的主要问题是外部知识更新和来源追溯，不是让模型学习一种新的语言风格。

如果把设备规程和工艺窗口直接微调进模型，文档更新以后需要重新训练，而且很难确认某个答案对应哪一版资料。

RAG 更适合频繁更新、需要引用来源的知识。微调仍然有价值，可以用于路由、格式控制和领域表达，但不能代替受控知识检索。

当前项目没有做 Qwen 微调，也没有把演示数据训练进模型。

## 五、为什么需要混合检索

稠密检索擅长理解语义。用户说颗粒异常，文档写 particle 超标，二者仍然可能靠近。

稀疏检索擅长保留精确词项。WAT、OOC、设备编号和 Recipe 名称一旦被弱化，可能召回完全错误的资料。

半导体问题同时需要这两种能力，所以项目没有只选其中一路。

混合检索的关键不只是同时执行两路，还要解决融合。当前使用 RRF，通过排名而不是原始分数融合，减少尺度差异问题。

## 六、为什么需要重排

召回阶段的目标是尽量不漏掉正确资料，因此会保留多个候选。

生成阶段的上下文不能无限增长。无关父块会占用 token，也可能干扰模型。

交叉编码器能够同时读取问题和父块，更细致地判断相关性。它适合处理小规模候选，不适合直接扫描全部文档。

因此系统先用 BGE-M3 召回，再用 BGE Reranker Large 重排。这是典型的两阶段检索。

## 七、为什么需要 FAQ

固定高频问题不一定需要完整 RAG。

比如执行设备 PM 前需要核对什么。这类答案可以由领域人员维护成标准口径。

FAQ 命中以后直接返回，能够减少一次路由调用、检索、重排和生成，也减少生成模型对标准答案进行不必要改写。

FAQ 不是简单关键词匹配，而是标准问题向量与用户问题向量的余弦相似度匹配。当前阈值是零点八五。

## 八、为什么需要四种策略

不同问题的检索难度不同。

明确事实题适合 Direct。

宽泛研究题适合 HyDE，通过假设文本补充检索术语。

多因素排查适合 SubQuery，把一个大问题拆成多个证据方向。

依赖上文的追问适合 Backtracking，把问题改写成独立查询。

当前策略由 LLM 选择，但结果必须进入白名单。模型不能创建第五种策略，也不能自由调用未注册能力。

## 九、如何降低幻觉

我没有把降低幻觉等同于写一段更强的 Prompt。

第一层是限制数据范围，只使用指定资料。

第二层是领域过滤和重排，减少无关上下文。

第三层是独立 FAQ，固定高频标准答案。

第四层是无结果时直接拒答，不让模型零证据生成。

第五层是生成提示词，禁止补造参数、规格、控制限和文档版本。

第六层是来源展示，让用户知道答案依据。

第七层是高风险提醒，把停机、放行、参数修改和 PM 决策交回受控流程。

这些措施只能降低风险，不能保证绝对正确。生产化还需要句级引用、事实一致性检测、规则校验、权限过滤和人工复核。

## 十、如何理解当前评估

当前评估的价值是验证评估链路，不是证明系统已经达到生产水平。

五条教学题太少，也没有经过正式专家标注。它们可以帮助检查五个领域是否有基本召回，但不能支持准确率结论。

现有脚本固定使用 Direct，因此没有测试路由是否正确，也没有比较 HyDE、SubQuery 和 Backtracking。

RAGAS 当前只计算上下文精确度和召回率。两个指标的平均值只是项目自定义的检索综合分，不是官方意义上的总准确率。

## 十一、完整演示逐字稿

下面我演示三条路径。

第一条是 FAQ 路径。

我输入 OOC 和 OOS 有什么区别。系统先计算问题与三条 FAQ 的相似度。如果达到阈值，直接返回标准答案。响应中的 domain 是 faq，strategy 是 direct，source 是 spc_quality。

这个路径没有调用查询路由、文档检索、重排和最终生成模型。它验证的是标准答案快速返回。

第二条是知识检索路径。

我输入刻蚀腔体 particle 超标怎么排查。FAQ 没有命中以后，路由器识别为 equipment 领域。这个问题涉及多个排查方向，适合 SubQuery。

系统生成多个子查询，分别执行稠密和稀疏检索。RRF 融合后恢复 equipment_pm 父块，再生成带来源的回答。

回答会建议确认量测有效性、批次和腔体关联、异常时段、最近 PM、Recipe 变更、设备告警、腔体状态、耗材记录和历史趋势。

回答不会给出未经资料支持的具体拆装步骤和设备参数。

第三条是无答案路径。

我询问某个具体设备型号的 RF 功率应该改成多少。演示知识库没有该设备和受控参数。正确行为不是给出一个行业常见值，而是明确说明信息不足，并要求核对设备型号、Recipe 和最新受控文件。

这三条路径分别验证 FAQ、RAG 和拒答。

## 十二、故障排查逐字稿

项目中有一次比较典型的问题发生在父块入库阶段。

当时子块能够正常写入，父块写入失败。最初看起来像 Chroma 或网络问题，但继续看堆栈后发现，父块没有传 embedding，Chroma 因此尝试调用默认 Embedding 模型。

这个行为不符合当前设计。父块根本不参与向量检索，只需要按 parent_id 读取原文。默认模型下载既浪费资源，也可能因为模型缓存目录权限失败。

我最后在父块 upsert 时显式传入固定的一维向量，并让 parents collection 维度保持为一。然后重新构建索引，确认 semicon_kb 有六个子块，semicon_kb_parents 有五个父块，父块恢复能够正常工作。

这个问题给我的经验是，第三方组件的默认行为必须显式核对。只看自己调用的接口参数不够，还要知道缺省参数会触发什么副作用。

## 十三、生产化改进逐字稿

如果让我继续把这个项目做成企业可用系统，我不会第一步就更换更复杂的向量数据库。

我会先解决数据和评估问题。没有经过权限、版本和专家审核的资料，再强的检索系统也不能给出可信结果。没有正式评估集，也无法判断换模型或换数据库是否真正提升。

接下来解决安全和索引可靠性。包括密钥轮换、身份认证、文档权限、审计日志、版本化索引、原子切换和回滚。

然后完善多轮检索和引用。历史感知改写应该发生在 FAQ、路由和检索之前。引用应该精确到页码、章节和段落。

最后根据真实指标扩展性能。文档规模、并发和延迟要求达到一定程度以后，再决定是否引入 Milvus、Elasticsearch、Redis、GPU 服务和模型网关。

这套顺序能够避免为了架构复杂度而堆技术名词。

## 十四、总结话术

最后总结一下。

SemiconRAG 的目标是让半导体知识问答从自由生成变成有证据、有来源、有边界的生成。

离线侧完成多格式解析、OCR、父子块切分和双表示索引。在线侧通过 FAQ、领域路由、策略路由、混合检索、RRF、父块恢复和重排构建上下文。生成侧通过严格 Prompt、无答案拒答和高风险提醒控制输出。服务侧提供 FastAPI、SSE 和 MySQL 会话。

这个项目当前仍然是教学原型。它最有价值的地方不是一个高分，而是完整展示了 RAG 系统中每个环节的作用、错误模式和生产化边界。

如果面试岗位更偏算法，我会重点展开 BGE-M3、混合检索、RRF、重排和评估。如果岗位更偏 AI 应用，我会重点展开查询路由、四种策略、会话和可信回答。如果岗位更偏后端，我会重点展开 FastAPI、SSE、索引重建、降级、持久化和安全。

## 十五、常见追问逐字回答

### 这个项目真正使用大模型的地方有哪些

大模型主要用于 FAQ 未命中后的领域与策略路由、HyDE 假设文本、SubQuery 拆分、Backtracking 改写、最终答案生成和会话摘要。Embedding 和重排由本地模型完成。FAQ 相似度、RRF、父块恢复、元数据过滤和数据库操作由确定性代码完成。

### 稀疏检索是不是 BM25

不是。当前使用 BGE-M3 lexical weights，通过查询词项和文档词项的权重点积排序。代码没有使用完整 BM25 公式。

### 为什么用 Chroma

当前项目数据量小，目标是验证 RAG 链路。Chroma 本地持久化简单，适合原型。生产选型要根据数据规模、过滤、并发、可用性和运维能力决定。

### 为什么不用五个 collection

五个领域是业务分类，不等于必须使用五个物理 collection。当前通过 area 元数据过滤，物理上只有 children 和 parents 两个 collection。

### 为什么父块需要占位向量

因为 Chroma collection 要求写入向量。父块只按 id 读取，不参与向量检索。显式传一维占位向量可以避免 Chroma 自动调用默认模型。

### 为什么使用 RRF

稠密距离和稀疏点积分数的尺度不同。RRF 使用排名融合，不需要直接比较原始分数，工程实现简单稳定。

### 为什么使用父子块

子块提高检索定位精度，父块保留完整上下文。命中子块后恢复父块，能够平衡召回粒度和生成质量。

### 四种策略是否都经过完整评估

没有。当前评估脚本固定使用 Direct。其他策略已经实现，但还需要独立标注集和消融实验验证。

### 多轮对话是否完整支持

当前生成阶段会读取最近三轮和历史摘要，但检索查询没有完整使用历史。Backtracking 也只接收当前问题。因此它支持基础会话记忆，但没有完全解决多轮指代检索。

### 模型是否完全本地部署

不是。BGE-M3 和重排模型从本地路径加载。路由、查询改写、生成和摘要使用远程 GLM 兼容接口。

### 如何证明项目有效

当前可以证明完整链路、索引结构和演示样例能够运行。不能证明生产准确率和业务收益。正式效果需要专家标注集、可复现报告和真实试点。

### 如果模型服务不可用会怎样

FAQ 已经加载时仍然可以返回标准答案。路由和策略改写有固定回退。最终生成依赖远程模型，失败时返回统一错误。生产环境还需要更完善的本地降级模型或模板回答。

### 系统会不会直接控制设备

不会。当前系统只提供知识查询和排查线索。停机、放行、参数修改、PM 和危险作业必须由授权人员按照最新受控文件执行。

### 这个项目最需要优先修复什么

第一优先级是轮换明文密钥和增加接口鉴权。第二优先级是建立专家标注评估集。第三优先级是实现版本化索引和原子切换。之后再优化多轮检索和性能。

### PIMS

常用于指工艺信息管理系统。它保存或展示制造过程中的工艺数据、参数和趋势。不同企业对 PIMS 的具体全称和边界可能不同，面试时应以目标企业实际系统为准。当前项目没有接入。

Manufacturing Execution System 的缩写，中文是制造执行系统。它记录批次、工序、设备、Recipe、人员和生产进度等现场执行信息。当前项目没有接入。

项目的问答总编排组件。它按顺序协调 FAQ、查询路由、检索、生成、流式输出和会话保存。

### VectorStore

项目对 Chroma 和内存稀疏索引的统一封装。它负责写入子块和父块、执行混合检索、恢复父块和调用重排。

### FAQStore

项目的 FAQ 管理组件。它负责读取 FAQ 文件、生成标准问题向量、计算相似度和热重载。

### Generator

项目的文本生成组件。它负责普通回答、流式回答、带历史回答、闲聊回答和会话摘要。

### 稠密检索

将查询和文档编码为固定维度向量，通过向量距离寻找语义相近内容。

### 稀疏检索

使用少量非零词项权重表示文本，更重视关键词、缩写和编号。

### RRF

倒数排名融合。它根据不同检索列表中的排名累加分数。

### AI

Artificial Intelligence 的缩写，中文是人工智能。本项目中的 AI 主要承担自然语言理解、查询改写、路由判断、回答生成和摘要，不负责直接执行生产决策。

### LLM

Large Language Model 的缩写，中文是大语言模型。它能够理解和生成自然语言。本项目使用 LLM 选择路由和策略，并生成最终回答。

### RAG

Retrieval-Augmented Generation 的缩写，中文是检索增强生成。它先从知识库检索证据，再让大模型根据证据回答。作用是补充外部知识、支持知识更新并提高答案可追溯性。

### FAQ

Frequently Asked Questions 的缩写，中文是常见问题集。它保存高频问题和标准答案。命中以后直接返回，可以降低延迟、调用成本和回答口径漂移。

### OCR

Optical Character Recognition 的缩写，中文是光学字符识别。它把图片或扫描文档中的文字转换成可以切分和检索的文本。

### Embedding

中文常称向量表示或文本嵌入。它把文本转换为一组数字。语义越接近的文本，其向量通常越接近。项目用它实现问题与知识块的语义匹配。

### BGE-M3

当前项目使用的 Embedding 模型。它同时生成稠密向量和稀疏词项权重，使同一个模型能够兼顾语义召回和精确词项召回。

### lexical weights

中文是词项权重。它表示某些 token 对当前文本的重要程度。项目使用它计算查询与子块的稀疏相关性。

### token

模型处理文本时的基本单位。一个 token 可能对应一个字、一个词或词的一部分。模型输入长度、生成成本和响应时间通常都与 token 数量有关。

### Chroma

当前项目使用的向量数据库。它负责持久化子块向量、文本和元数据，也负责根据查询向量返回相似子块。

### collection

Chroma 中组织一组数据的逻辑集合。作用类似数据库中的表。项目使用 children collection 保存可检索子块，使用 parents collection 保存父块原文。

### children

表示子块集合。子块体积较小，主要用于提高检索定位精度。

### parents

表示父块集合。父块体积较大，主要用于为生成模型提供更完整的上下文。

### id

表示唯一标识。它用于区分每条文档记录、去除重复候选和精确读取数据。

### parent_id

表示父块标识。每个子块都通过 parent_id 指向所属父块。检索命中子块后，系统用它恢复父块。

### source

表示知识来源。当前值来自文件名，用于在回答中展示资料来源并支持指定文档过滤。

### file_path

表示原始文件路径。它用于定位资料在磁盘中的位置。

### timestamp

表示时间戳。当前记录文档进入处理链路的时间。生产环境还需要独立保存文档生效时间和失效时间。

### document_id

表示文档稳定标识。文件名或路径变化时，document_id 仍应能够标识同一份业务文档。

### content_hash

表示根据文档内容计算出的摘要值。内容没有变化时结果相同，内容改变时结果通常改变，可用于增量更新和重复检测。

### domain

表示请求大类。它决定系统是进入专业知识链路还是闲聊链路。

### knowledge

表示知识类请求。系统会进入领域判断、策略选择、知识检索和证据生成。

### chitchat

表示闲聊类请求，例如问候或与半导体知识无关的问题。系统不需要检索专业知识库。

### area

表示知识所属的业务领域。它用于给稠密检索和稀疏检索添加范围过滤。

### process

表示工艺整合领域。它覆盖光刻、刻蚀、薄膜、扩散、CMP 和工艺窗口等内容。

### equipment

表示设备维护领域。它覆盖设备型号、腔体、PM、告警、耗材和设备状态等内容。

### yield

表示良率分析领域。它覆盖 WAT、缺陷分布、工艺履历、设备关联和批次趋势等内容。

### cleanroom

表示洁净室和环境安全领域。它覆盖区域规范、防污染、化学品、人员资质和安全要求。

### quality

表示制程质量领域。它覆盖 SPC、OOC、OOS、量测系统、控制规则和规格文件。

### strategy

表示检索策略。它决定系统直接检索原问题，还是先对问题进行生成、拆分或改写。

### Direct

表示直接检索。系统不改写用户问题，直接使用原问题查询知识库。它适合术语明确的事实题，延迟也最低。

### HyDE

Hypothetical Document Embeddings 的缩写。系统先生成一段假设答案，再用假设文本检索。它用于给宽泛问题补充可能出现在专业资料中的术语。

### SubQuery

表示子查询拆分。系统把一个复杂问题拆成多个相对独立的小问题，分别检索后合并结果。它适合多因素排查。

### Backtracking

表示回溯式改写。系统把依赖上文、表达过短或指代不清的问题改写成独立查询。当前项目还没有把完整会话历史送入这一步。

### QueryRouter

表示查询路由器。它调用大语言模型判断 domain、area 和 strategy，再用白名单检查结果。

### JSON

JavaScript Object Notation 的缩写，是一种结构化文本格式。项目要求路由模型返回 JSON，便于程序读取固定字段并校验取值。

### Pydantic

Python 数据校验库。它可以声明字段类型、必填项和取值约束。项目用它校验接口请求、FAQ 数据和响应结构。

### Prompt

发送给大语言模型的指令和上下文。Prompt 规定模型要完成的任务、可以使用的资料、输出格式和禁止行为。

### session_id

表示会话标识。相同 session_id 的多轮问答会读取同一组历史记录和摘要。

### question

表示用户当前问题。它是问答接口的必填字段。

### answer

表示系统最终回答。非流式接口一次性返回完整 answer。

### source_filter

表示来源过滤条件。用户指定它以后，系统只在对应 source 中匹配 FAQ 或检索文档。

### stream

表示是否启用流式输出。值为 true 时，接口使用 SSE 分段返回内容。

### chunk

表示一个文本块。在文档处理阶段，chunk 可以指切分后的知识块。在流式输出阶段，chunk 表示模型刚刚生成的一小段增量文字。

### elapsed_ms

表示请求耗时，单位为毫秒。当前代码从问答开始计时，到答案生成结束时停止，不包含后续后台摘要时间。

### FastAPI

Python Web 接口框架。项目使用它定义请求模型、路由和响应，并向前端提供问答服务。

### API

Application Programming Interface 的缩写，中文是应用程序接口。它让前端或其他服务能够以固定格式调用后端能力。

### HTTP

Hypertext Transfer Protocol 的缩写，中文是超文本传输协议。浏览器和 FastAPI 之间的请求与响应基于 HTTP。

### POST

HTTP 请求方法之一，通常用于提交数据或触发操作。问答、重建索引和 FAQ 重载都使用 POST。

### GET

HTTP 请求方法之一，通常用于读取信息。项目健康检查使用 GET。

### SSE

Server-Sent Events 的缩写，中文是服务端推送事件。它让后端通过一条 HTTP 连接持续向浏览器发送文本事件。

### WebSocket

一种全双工通信协议。客户端和服务端都可以随时发送消息。当前项目只需要服务端持续推送文本，所以使用 SSE，没有使用 WebSocket。

### CORS

Cross-Origin Resource Sharing 的缩写，中文是跨域资源共享。它决定哪些网页来源可以调用接口。生产环境应该使用允许来源白名单。

### MySQL

关系数据库。当前项目使用它保存每轮会话、来源、耗时和会话摘要。

### Redis

高性能内存数据存储，常用于缓存、会话和分布式锁。当前项目没有接入 Redis，只把它作为未来多实例和缓存场景的候选组件。

### Milvus

面向大规模向量检索的数据库。它支持分布式存储、索引和过滤。当前项目使用 Chroma，没有使用 Milvus。

### Elasticsearch

搜索与分析引擎，擅长倒排索引、关键词检索和结构化过滤。它可以作为大规模稀疏检索的生产化选择。

### OpenSearch

开源搜索与分析引擎，功能方向与 Elasticsearch 相近。它也可以承载关键词检索、过滤和日志分析。

### Reranker

表示重排器。它对第一阶段召回的少量候选重新打分，用于把与问题更相关的资料排到前面。

### CrossEncoder

表示交叉编码器。它把问题和候选文档一起输入模型，使二者充分交互。准确性通常高于独立向量比较，但计算成本更高。

### RAGAS

用于评估 RAG 系统的工具框架。当前项目通过它计算上下文精确度和上下文召回率。

### context_precision

表示上下文精确度。它关注检索到的内容中有多少真正有助于回答问题。分数低通常说明噪声较多。

### context_recall

表示上下文召回率。它关注标准答案所需的证据是否被检索结果覆盖。分数低通常说明关键资料遗漏。

### ragas_score

当前项目报告中的自定义综合字段。它只是 context_precision 与 context_recall 的算术平均，不等于答案准确率。

### Recall at K

表示前 K 个检索结果的召回情况。它用来判断有限候选中是否已经包含正确资料。

### MRR

Mean Reciprocal Rank 的缩写，中文是平均倒数排名。它重点衡量第一个正确结果出现得有多靠前。

### NDCG

Normalized Discounted Cumulative Gain 的缩写，中文是归一化折损累计增益。它同时考虑结果相关程度和排序位置。

### P95

表示第九十五百分位延迟。它说明百分之九十五的请求都能在这个时间以内完成，比只看平均延迟更能反映慢请求。

### CPU

中央处理器。当前本地 Embedding 和重排配置主要使用 CPU，兼容性较好，但模型推理速度通常低于 GPU。

### GPU

图形处理器。它擅长并行矩阵计算，可以明显提升 Embedding、重排和生成模型的吞吐与响应速度。

### FP16

十六位浮点数格式。它可以减少模型显存占用和部分计算成本。当前配置没有启用。

评估实现位于 rag_qa/eval。
