# 技术方面

## 一、开场话术

### 40 秒自我介绍

“我主要关注 Python 后端和 RAG 应用开发。最近做的 SemiconRAG 是一个面向晶圆制造知识问答的教学原型。我把原有问答链路组织成工艺整合、设备维护、良率分析、洁净室和质量控制五个领域，做了文档解析、父子块索引、BGE-M3 稠密与稀疏检索、FAQ 优先路由、可选重排，以及 FastAPI 问答接口和会话记录。这个项目让我比较系统地处理了资料来源、检索定位和缺证据回答的问题。我的实际独立负责范围是 `[待本人填写，并对照提交记录]`。”

### 40—60 秒项目架构介绍

“离线侧从 `data/semicon/` 读取 Markdown 等支持的文件，按中文段落和标点递归切成父块、子块，给子块生成 BGE-M3 稠密向量和稀疏词项权重。子块与父块分别放在两个 Chroma collection，稀疏索引保存在进程内。在线侧先做独立 FAQ 匹配；没命中就用 LLM 判断闲聊或知识问答、选择五个领域和四种检索策略。知识问答在选定领域内做稠密与稀疏召回，通过 RRF 融合，恢复父块，必要时用 CrossEncoder 重排，最后让生成模型依据带来源的上下文作答。FastAPI 提供普通响应和 SSE 流式响应，MySQL 存会话与摘要。”

## 二、场景、数据与边界

### 问题：项目服务什么场景？五个知识库怎么组织？

**回答：**“演示场景包括 `process` 工艺整合、`equipment` 设备维护、`yield` 良率、`cleanroom` 洁净室和 `quality` 质量控制。它们是数据目录与 `area` 元数据的五个领域，不是五个物理数据库。当前 Chroma 只有子块和父块两个 collection。用户指定 `source_filter` 时，按文件 stem 限定资料，并优先于自动领域过滤。”

### 问题：数据来源、数据量和更新频率是多少？

**回答：**“默认目录里有五份明确标注为演示用途的 Markdown 资料，独立 FAQ 文件有三条记录；半导体教学评估集有五道题。这些数量是仓库现状，不代表真实企业文档量。现有流程通过脚本或接口全量重建索引，没有增量更新、自动版本失效或定时同步。被改动资料的更新频率由使用者操作决定，仓库没有生产更新周期数据。”

### 问题：给你 PDF/Markdown，从零设计 RAG 怎么做？

**回答：**“先确认文件量、文本层或扫描件占比、表格图片比例、权限范围、更新频率和回答时延。针对当前原型，可以沿用 PDF/Markdown 加载、OCR、父子块、Chroma 和来源展示。但要给真实产线用，还需要受控文档编号、版本和生效范围、权限过滤、页面级引用、专家审核、索引切换与回滚，以及完整评估。这些属于下一步设计。”

## 三、数据预处理与切块

### 问题：文档如何处理、PDF 如何切块？

**回答：**“加载器支持 PDF、DOCX、PPT/PPTX、图片、Markdown 和 TXT；部分格式通过 OCR 处理扫描内容。文档处理器从目录推导 `area`，从文件名推导 `source`，然后先切父块、再从父块切子块。当前配置为父块 1200、子块 300、重叠 50，切分器的 `length_function` 是 `len`，即字符长度，不是 token 数。优先按段落、换行和标点边界递归切分。每个子块带 `parent_id`，检索后用它恢复父块。”

### 问题：为什么采用父子块？切块大小怎么确定？

**回答：**“小子块便于命中具体术语，较大的父块给模型保留前后条件。1200/300/50 是当前配置，仓库里没有能证明它们优于其他参数的消融实验。下一步会按题型比较 Recall@K、答案正确性、上下文长度和时延，再调整大小及 overlap；尤其检查工艺步骤、单位、否定条件是否在边界被切断。”

### 问题：表格、图片和跨页表怎么处理？

**回答：**“现有加载器能够读取多种格式并进行 OCR，但项目没有完整的表格结构恢复、跨页表合并、图片坐标和页码级引用。真实资料要额外保存表题、表头、单位、行列关系、页码和适用版本，大表按表题与表头重复的行组切分；扫描质量差的页要人工抽检。不能把当前通用字符切分说成已完成复杂表格治理。”

### 问题：脏数据、重复资料和增量更新怎么办？

**回答：**“当前加载时，同一目录同名不同格式的候选文件只保留一份；加载失败会记录并跳过。全量建索引先清空旧 collection 再写新数据，因此失败时有旧索引被清掉的风险。生产化我会使用稳定文档 ID、内容 hash 与版本号，先构建和校验新索引，再切换活动版本；解析失败进入隔离清单并可回滚。”

## 四、Embedding、向量库与数据库

### 问题：为什么选 BGE-M3？能直接换模型吗？

**回答：**“当前实现用本地 BGE-M3 同时输出稠密向量和稀疏 lexical weights，适合演示语义与术语两路检索；配置里的稠密向量为 1024 维。选择依据应由中文领域检索评估、资源和延迟来验证，仓库尚无正式对比实验。换 embedding 模型时需重算文档向量和稀疏权重、重建索引并对比效果，即便新旧维度相同也不能混用。”

### 问题：为什么用 Chroma，不用 Milvus/FAISS/ES/pgvector？

**回答：**“这是本地教学原型，Chroma 持久化方便，两个 collection 足以存子块向量和父块原文。仓库虽可能安装其他库，但当前在线检索不是 Milvus、FAISS、ES 或 pgvector。若面对更大规模或多租户，再根据文档量、过滤条件、写入频率、QPS 和运维条件做基准测试后选型。”

### 问题：Redis、Milvus、MySQL 怎么分工？

**回答：**“本项目的实际分工是 Chroma 存子块向量及父块原文，进程内维护 BGE-M3 稀疏索引，MySQL 存会话问答和摘要，FAQ 保存在 JSON 文件并在加载时预计算问题向量。没有 Redis 缓存和 Milvus；原始演示文档保存在本地目录。若被问到三者组合，可以作为假设设计讨论，不能说成项目现状。”

### 问题：向量索引参数怎么选？

**回答：**“当前由 Chroma 管理向量索引，代码未做 FLAT、IVF、PQ 与 HNSW 的专项对照实验。小规模原型先确认检索正确性；规模扩大后，再用高精度检索作基线，按召回、延迟、内存和构建成本选择索引及参数。”

## 五、检索、融合与重排

### 问题：语义、全文和混合检索分别怎么用？

**回答：**“当前稠密路调用 Chroma 相似度检索；稀疏路是 BGE-M3 的 lexical weights 在内存中计算词项权重乘积。两路以 RRF 按排名融合，避免直接比较不同分数尺度。稀疏路不是 BM25，也不是独立全文搜索服务。对于设备编号和缩写，词项命中可能有帮助；对于改写问法，语义路可能有帮助，具体收益要靠评估集验证。”

### 问题：topK、topN 是多少？怎么定？

**回答：**“当前每条检索 query 的子块召回 `retrieval_k=5`，父块最终保留 `candidate_m=3`；SubQuery 会对多个子问题分别召回再按子块 ID 去重。K=5、N=3 都是配置值，不是经正式寻优后的最优点。调参时先看正确证据是否进入粗召回，再看父块重排后是否进入上下文，并同时记录时延和 token 成本。”

### 问题：为什么还要 rerank？

**回答：**“稠密向量和稀疏权重先完成较快的粗召回。可选的 BGE CrossEncoder 对 query 与候选父块逐对评分，再截取前 3 个；配置默认启用，但候选父块不超过 3 个时会直接返回，不会实际运行重排模型。首个需要重排的请求才懒加载模型。是否值得开启，应通过同一评估集比较质量、首请求加载和常态延迟。”

### 问题：检索不准怎么定位？

**回答：**“先检查目标资料是否在默认目录并成功加载；再看相关条件有没有被切断、子块有没有被领域过滤掉；接着看稠密和稀疏各自召回、RRF 排名、父块恢复和重排结果；最后检查生成时的上下文和答案。当前系统有文本日志，但没有统一 request ID 和全链路 trace，生产化需要补上，才能稳定定位每一层。”

## 六、FAQ、路由与四种策略

### 问题：FAQ + RAG 怎么路由？分类错了怎么办？

**回答：**“先将问题与启用 FAQ 的标准问题向量做余弦相似度匹配，当前阈值为 0.85；命中就返回标准答案，不调用路由和生成模型。没命中时 LLM 返回 `knowledge/chitchat`、五选一的 `area` 和四选一的 `strategy`，服务端校验枚举值，异常时退到 `knowledge + process + direct`。这个阈值和路由没有用大规模标注集校准，错路由仍可能造成漏检；需要领域混淆矩阵、误命中负例和回退机制。”

### 问题：Direct、HyDE、SubQuery、Backtracking 有什么区别？

**回答：**“Direct 直接检索原问题；HyDE 先让模型生成假设性文本作为检索 query，假设文本不作为答案；SubQuery 把多因素问题拆成最多四个子问题分别检索；Backtracking 把追问改写成独立问题。当前检索策略生成主要使用本轮问题，历史没有稳定传入 Backtracking，所以还不能说它已解决多轮指代。”

### 问题：短问题‘查一下这个’怎么处理？

**回答：**“当前最近对话和摘要会进入生成提示词，但检索阶段不一定能正确理解‘这个’。实际演示应要求用户明确设备、文档或问题对象。下一步可以先从最近轮次提取指代对象，用保留原意的改写 query 检索；仍不明确时先澄清，不应直接凭模糊候选作答。”

## 七、多轮上下文与记忆

### 问题：历史太长、用户换话题怎么办？

**回答：**“MySQL 存问答记录，生成时读取最近 3 轮和更早摘要；摘要更新在后台线程执行。当前没有完善的话题切换识别，也没有会话级并发顺序保证。若要生产化，应按会话串行或用版本号保护摘要，明确会话过期和删除规则，并把历史感知改写放到检索前。”

### 问题：历史与当前信息冲突时怎么办？

**回答：**“对用户查询条件，以本轮明确输入为准；对工艺事实、放行标准和设备操作，以适用产品、设备及最新版受控文件为准。当前演示数据不包含实时业务状态，也没有企业身份与授权系统，因此无法处理真实权限和生产状态冲突。”

## 八、幻觉、安全与权限

### 问题：RAG 如何减少幻觉？

**回答：**“当前主要通过检索上下文、来源标题和提示词约束：只根据资料回答，缺信息说明不足，不能编造工艺参数、设备规格和控制限。无检索内容时返回无依据提示。提示词不是可靠性证明，仓库还没有引用正确率、答案忠实度和错误参数专项评估；真实使用前必须加专家审核、受控版本和逐条引用定位。”

### 问题：提示词注入和多租户越权怎么防？

**回答：**“当前原型没有认证、租户隔离或文档 ACL；`area` 与 `source_filter` 是检索范围条件，不是安全边界。生产化要在服务端认证，并在检索时强制绑定租户、知识库和权限过滤；外部文档只作数据，不能执行其中的指令；重建索引和 FAQ 重载接口还要加管理权限与审计。不能说现有项目已经防住越权或提示词注入。”

### 问题：涉及停机、放行或参数修改，系统能直接下指令吗？

**回答：**“不能。演示资料不是厂内受控文件；当前提示词会要求核对最新版受控文件和审批流程。真实系统还需把设备型号、腔体、产品、Recipe 版本和生效时间核对清楚，并把高风险建议交由授权人员审批。”

## 九、性能、部署与接口

### 问题：回答慢怎么优化？

**回答：**“先分阶段测 FAQ 匹配、路由 LLM、Query 改写、Embedding、双路召回、重排、首 token 和完整生成的耗时，再找瓶颈。当前 API 主要有端到端 `elapsed_ms`，尚无分阶段 P95 指标。可通过减少不必要的策略调用、控制候选量、缓存稳定的热点问法和流式输出改善体验，但是否有效要压测验证。当前没有 Redis 缓存和明确并发容量数据。”

### 问题：FastAPI/Docker 上线后出问题怎么排查？

**回答：**“当前服务用 FastAPI，`POST /api/ask` 可返回普通 JSON 或 SSE，`GET /api/health` 返回模型名、collection 名和子块数，另有索引重建和 FAQ 重载接口。仓库没有可据以宣称的 Docker 生产部署。若线上化，先看请求与应用日志、模型权重路径、Chroma 状态、MySQL 和外部 LLM 接口；然后补 request ID、readiness 和分阶段耗时。现有 health 是基础状态信息，不能替代依赖就绪检查。”

### 问题：SSE 与 WebSocket 怎么选？

**回答：**“当前问答采用 SSE，服务端持续推送 `meta`、`chunk`、`done` 等事件，适合单向文本流。项目没有 WebSocket 实现。以后如需更复杂的双向实时协同，再评估 WebSocket。”

### 问题：MCP 和 Function Calling 用了吗？

**回答：**“当前问答链路没有 MCP Server，也没有给模型开放实时业务工具。Function Calling 是模型按工具 schema 选择调用和生成参数的机制；MCP 约定工具、资源等如何对外提供。如果未来接入设备或质量系统，要由服务端验证参数、身份、权限、超时和审计，不能让模型文本直接触发高风险操作。”

## 十、评估、交付与软技能

### 问题：准确率、召回率和业务效果是多少？

**回答：**“目前不能报生产准确率或提效百分比。仓库有五道半导体教学评估题，未经过领域专家形成正式基线。现有 RAGAS 运行器使用 Direct 检索路径，统计上下文精确度和召回率，不能代表 FAQ、路由、四策略和最终答案的端到端质量。下一步需要增加分层标注集，报告检索 Recall@K、路由准确性、答案忠实度、引用正确率、拒答质量以及 P50/P95 时延，并注明样本量和版本。”

### 问题：客户觉得效果不好、工期又到了怎么办？

**回答：**“先要到失败问题和期望答案，确认资料是否在范围内，并按解析、过滤、召回、重排、生成分层复现。对已能稳定回答的范围给出可检查的样例和来源；对高风险或资料缺失问题明确限制、人工复核路径与后续迭代项。当前项目没有真实客户交付记录，这里是处理方法，不是既有经历。”

### 问题：如果做成企业可用版本，先做什么？

**回答：**“优先接入经授权的真实受控资料，补文档版本、生效范围和权限标签；把全量清空重建改为新索引构建、校验、切换和回滚；建立专家标注的分层评估集；再补会话隔离、审计、分阶段指标和容量压测。当前使用兼容 API 调用外部生成模型，不能声称完全内网部署。”

## 十一、模型基础与延伸追问

### 问题：Transformer、自注意力、temperature/top_p/top_k 怎么回答？

**回答：**“Transformer 通过注意力关联不同 token；自注意力中用 Q 与 K 计算相关性，再对 V 加权汇聚。temperature 调整采样随机性，top_k 限制候选数量，top_p 限制累计概率候选集合。知识问答降低随机性有帮助，但不能替代检索质量和证据校验。当前项目的 `config.ini` 配置了生成和策略调用温度；不要把一般模型知识说成项目独有优化。”

### 问题：BERT 为什么不能直接替代检索 embedding？

**回答：**“通用 BERT 的预训练目标不等同于 query 与 passage 的相似度检索；专用 embedding 模型通常针对检索做过优化。是否替换仍要在本项目问题集上比较召回、时延和资源，而不能只看模型名称。当前实现使用 BGE-M3，没有 BERT 对照实验。”

### 问题：CrossEncoder 分数能当概率吗？

**回答：**“不能直接把重排分数解读为答案正确概率。它主要用于同一次候选排序；如果要设跨请求阈值，必须用标注集校准。当前代码只按分数排序取前几个父块。”

## 十二、面试前核对清单

1. 写清自己的真实职责、提交或演示证据、一次遇到的问题和验证结果；没有数据就讲复现和检查方法。
2. 记住实际配置：父块 1200 字符、子块 300 字符、重叠 50 字符、子块每 query 取 5 个、最终父块取 3 个、FAQ 阈值 0.85；这些是配置，不是最优实验结论。
3. 区分五个**领域**与两个 Chroma **collection**；BGE-M3 稀疏 lexical weights 与 BM25 不是同一实现。
4. 区分已实现的来源标题与尚未实现的页面级可点击引用、权限过滤、增量索引和生产效果评估。
5. 人事信息、实际贡献、客户与业务效果均以本人可核验事实填写；不要使用模板中的示例数字或假想企业能力。
